## 2. 账户与登录体系

### 2.1 需求

- **完整注册 + 登录**，复用**调度中心**的身份体系，不做第二套账号
- **多设备无限登录**（同一账户同时登录 PC / 手机 / 协作端）
- 权益与用量**按账户额度控制**，不按设备数控制
- 手机与 PC **共享同一份额度**

### 2.2 现状（证据）

- 客户端已有账户会话服务：`packages/host/account-session`，接口
  `/api/qianshou/account/state`、`/account/me` 返回账号角色、档位、余额（本机实测 **200**）。
- **角色只认服务端**：我此前**删除了**"读本地文件里的 role"那条路——
  改一行 JSON 就成管理员是审查里最严重的一条。这条防线**必须保留**。
- 档位定义：`tiers.ts` — `basic` 普通版 39 元 / 390 SP，`plus` 高级版 99 / 990，`max` Max 版。
- 上游调度中心已有：`/api/v8/auth`、`we_accounts`、`AccountRole`（`personal|enterprise|channel|admin`，
  从**数据库行**读取），`economy/*`（余额、流水、充值）。

### 2.3 缺口

| # | 缺口 | 说明 |
|---|---|---|
| G5 | **多设备并发策略未定义** | "无限设备"需明确：是无限**并发**还是无限**设备数**（后者更常见、更安全）。建议：设备数不设限，**并发会话**按档位限制 |
| G6 | **设备与会话解耦未落** | 需明确"额度在服务端、会话可撤销、设备可踢"的模型 |

## 3. 管理后台（运营后台）

### 3.1 需求清单（你列的）

登录 / 注册 / 账号 / 额度 / 充值 / 订阅 / 封禁解封 / 积分 / 使用额度 / 安装量 / 分布式算力

### 3.2 数据权威在哪（**这是最关键的判断**）

| 指标 | 权威来源 | 现状 |
|---|---|---|
| 账号、注册、登录 | 上游调度中心 `/api/v8/auth` + `we_accounts` | **已有** |
| 订阅、档位、额度 | 上游 `economy/*` | **已有** |
| 充值记录 | 上游 `economy/transactions` + `admin/deposit` | **已有** |
| 安装量、节点 | 上游 `/api/v8/workers/*` | **已有**，但有刷量风险（见 §3.4）|
| **全站逐次用量** | 现在**只在客户端本地**（`model-gateway/src/ledger.ts`）| **缺口：未上报** |
| 封禁 / 解封 | 未见明确接口 | **缺口** |

### 3.3 架构结论（**不要做第三套系统**）

```
① 账户与计费面（权威在上游） → 运营后台【读上游 admin API】
② 用量面（逐次调用）         → 客户端本地账本【增量上报】→ 上游
③ 客户端运维面（本机绑定/审计）→ 留在应用内「设置 → 模型路由」
```

- **① 是你要的运营后台**：挂官方站，**独立子域 + 独立鉴权 + fail-closed**，
  **绝不与用户账号共用会话**、**绝不在客户端判断管理员**。
- **③ 不是运营后台**：现有「模型路由」控制台只管**这台机器**的网关绑定与本地审计。
  两个不能混，否则你会以为在看全站数据、其实是本机数据。

### 3.4 我在上游查到的三个真实隐患（**必须修，否则后台数字会骗你**）

1. `workers.py` 用了**三种不一致**的管理员判据（`is_admin` / `superadmin` / `channel_admin`），
   净效果是两类管理员各能看一半。**后台不要依赖这些路由做授权**，先统一。
2. `kick_worker` 把管理员判据放在**请求 body** 里（不是依赖）→ 可被绕。
3. `admin_fe.py:324` 的 `cancel_workload`（admin）**被同路径的 bearer 路由遮蔽**
   （FastAPI 取先注册的匹配，`admin_fe` 在 `workloads` 之后 include）→ **该管理操作实际失效**。
4. **无角色门槛阻止 `personal` 账号注册成 worker 节点** → 若"安装数"依赖 worker 注册，
   **任何人都能刷量**。展示时必须标注来源与可信度。

### 3.5 分期

| 期 | 内容 | 新后端工作量 |
|---|---|---|
| 一 | 后台接**已有** admin 路由：economy stats/transactions/deposit + workers + accounts | **几乎为零** |
| 二 | **用量上报**：客户端本地账本增量上报 → 全站逐次用量与聚合 | 需新增上报端点 + 聚合 |
| 三 | 封禁/解封、订阅生命周期（**必须 fail-closed**）| 需新增上游接口 |

## 4. 分布式算力（**你问的"调度接了吗"**）

### 4.1 现状（证据，非推断）

| 事实 | 证据 |
|---|---|
| `dispatch-adapter` 包**存在** | `packages/host/dispatch-adapter/src/index.ts` |
| 但它**没有挂进 web profile** | `--dump-config` 里只有 `qianshou-compute-core`、`compute-tools`、`ui-compute` |
| 算力工具**只有读与草稿** | `compute-core/src/tools.ts`：`compute_capabilities` / `compute_plan_draft` / `compute_workload_read` |
| **没有"提交任务"的工具** | 三个工具的描述都明写不提交、不扣费 |
| 适配器自己声明**不做真连** | 包注释："does not open sockets, discover endpoints, fetch task inputs, upload media, price work, or settle payments" |

**结论：调度（dispatch）没有接入运行时；分布式算力目前是"可读、可存草稿"的半接入形态，不能真正下单。**

### 4.2 缺什么才能真跑

1. **连接器（connector）**：由部署提供，负责鉴权与物理传输 —— 现在缺失
2. **提交工具**：`compute_workload_submit`（现在不存在）
3. **租约/分片/artifact 传输**：协议在 `算力底座API利用映射.zh.md` 里有映射，未落代码
4. **结算**：`dispatch-adapter` 明确不做结算

### 4.3 「关键字是什么、如何触发」——**这里有两条路，我建议走第一条**

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **A. 工具触发（仓库现在的选择）** | 模型判断任务适合并行 → 调 `compute_capabilities` → 提议草稿 → **问你预算** → 确认后才提交 | 用户不需要背关键字；意图由语义判断 | 依赖模型判断，需清晰的能力目录 |
| **B. 关键词触发** | 用户打 `/算力 …` 或"用分布式算力跑…" | 可预期、可教 | 用户要记语法；与自然对话冲突 |

**建议 A**，理由：本产品定位是"帮你干活"，让用户记魔法词是**把复杂度推给用户**。
但需要一个**显式确认点**（草案 → 用户点确认 → 提交），因为涉及花钱。

**触发条件建议**（写进工具描述，让模型有可依的判据）：
- 任务可**并行切分**（多文件、多语料、多方案候选、批量生成）
- 本地算**慢到影响体验**（大模型推理、长视频、批量转码）
- 用户明确表达"要快/要并行/不限本地资源"
