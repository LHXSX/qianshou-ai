## Guangzhou media node channel

`profile_version` in both advertised capabilities and `envelope.spec.media_input` is a strict integer of at least 1 (within JavaScript's safe integer range), matching Shanghai's official profile revisions. Strings such as `"1"`, booleans and fractional numbers are refused. A dispatch envelope requires the full closed Shanghai `media_input` fields: capability, mode, prompt, negative_prompt, quality, orientation, seconds, assets, profile_id and profile_version, with Shanghai's optional defaults for negative_prompt/assets/image seconds. `spec.task_type` must match `image_generate` or `video_generate`. Asset roles must match the selected mode; hidden legacy inputs, parameters, executable URLs and redundant generation are refused. Caller/node-supplied billing/non_billable/price/charge claims are forbidden; only Shanghai's independently signed, complete frozen authorization may carry price control terms and additional dispatch request fields are refused. Neither a zero price nor a research label grants an authorization or changes settlement behavior.

`mediaNodes` enables routes on the existing `webServer`; omission registers none. Configure `storePath` in an absolute private `0700` directory, fixed Shanghai HTTPS `accountApiOrigin`, `heartbeatIntervalMs`, `heartbeatTimeoutMs` (at least twice the interval), and `maxLongPollRequests`. Private trials may use 15000/45000 milliseconds and at most 64 polls. SQLite is `0600`, stores credential hashes, and requires the supported Node 22.19+ runtime; its current experimental API warning is expected. Each database supports one gateway runtime. Production multi-instance coordination and retention require separate deployment work.

Device control routes use POST JSON, reject browser Origin/Cookie, duplicate Authorization, compressed or oversized bodies (128 KiB), and never use Guangzhou's browser owner session. `/v1/nodes/register` verifies the request's Shanghai account Bearer and accepts `{deviceId,deviceToken,adapterVersion,capabilityRevision,capabilities,maxConcurrency}`. The Host generates and privately saves its 32-byte base64url token before registration; exact retries preserve the epoch. Profile entries have `profile_id`, `profile_version`, `model_sha256`, `workflow_sha256`, and `validation_receipt_sha256`. Same revision with changed data or owner/token binding conflicts. Register returns the same token plus `{ok,deviceId,connectionId,connectionEpoch,heartbeatIntervalMs,heartbeatTimeoutMs}`.

Other routes use device Bearer. `/reconnect` accepts `{deviceId,capabilityRevision}`, advances the epoch, and returns connection fields. `/channel` accepts `{deviceId,connectionEpoch,afterSequence,waitMs}` with `0 ≤ waitMs ≤ 25000`, and returns connection fields plus `online`, `sequence`, and `tasks`. Task fields are `{sequence,deviceId,taskId,attemptId,leaseEpoch,leaseExpiresAt,quoteId,authorizationId,envelope,stage,expired}`. A new epoch's first snapshot includes unfinished tasks at or before the saved cursor. The Host must reconcile persisted attempts/external job ids and commit each inbox item before advancing its cursor; recovery never authorizes another model POST. `/heartbeat` accepts `{deviceId,connectionEpoch,capabilityRevision,freeSlots,runningAttemptIds,freeVramMb,availableSeconds}` and returns the epoch/online state. Only recovered current epochs publish supply. Timeout projects zero idle slots; unfinished attempts still reserve slots after lease expiry. `/disconnect` accepts `{deviceId,connectionEpoch}`, immediately withdraws supply, and preserves tasks. `/events` accepts `{deviceId,connectionEpoch,taskId,attemptId,leaseEpoch,sequence,stage,percent?}`. Real finite percent may be 0–100. Events are idempotent, lease-bound and cannot regress stage or node terminal state; model completion stops at `awaiting_settlement`, never order `completed` or a charge.

`dispatchCredentialRef` names a credential-service secret for Shanghai-only internal metadata routes. The durable global journal exposes read/ack pages, original task reconciliation, independent Ed25519 result ingress and idempotent committed settlement notices. Formal dispatch verifies Shanghai's complete signed buyer/contributor/task/lease/price binding; unknown submissions never create a second attempt. `exchangeOrigin` and `exchangeCredentialRef` connect only the existing Guangzhou verifier. Default directory capabilities remain self-reported and unavailable; fresh independently verified official receipt bindings may qualify an exact device/owner/profile, and Shanghai still enforces supply policy.

Device-bound input read tickets preserve the original buyer/role/version under a live lease, and fixed read proxies verify complete length and SHA. Order-current relays Shanghai full-spec signatures; task-status restores original verdict/settlement. Independent official runtime installation manifests and exact owner/device/worker qualifications stay closed without reviewed release/license materials. The source candidate carries authenticated buyer asset tickets, device-bound result upload tickets and bounded raw byte uploads without shipping service or COS credentials. The existing Python service performs immutable-version file verification and signed result delivery. Official release, profile prices and actual device validation are required; absent evidence leaves profiles unavailable. See [the formal media contract](../../../deploy/native-h3-20260927/FORMAL-MEDIA-PORT.md) and [connection decision](../../../.agents/notes/implemented/architecture/2026-09-29-guangzhou-media-node-channel.md). H3 `18802` remains a separate trial bridge. These source, loopback and isolated CPU decoder checks establish neither production deployment nor native Windows acceptance. Run `node --experimental-strip-types --test packages/host/model-gateway/tests/media-control-feed.node-test.mjs packages/host/model-gateway/tests/media-node-channel.node-test.mjs packages/host/model-gateway/tests/plugin-license-bearer.node-test.mjs` for control, recovery, identity and asset carrier checks.

## Plugin directory contract

When the host provides `webServer`, the gateway registers `GET /qianshou-market/plugins` as a public, read-only route. It returns `{ "listings": [] }` until an operator configures `marketCatalogPath` with an absolute path to a reviewed JSON file. The route is outside `/api` because the Mac plugin catalog fetches without a browser session cookie. Other HTTP methods return 405. An unreadable, oversized or invalid configured file returns 503 and exposes no partial catalogue.

The file has `version: 1` and a `listings` array of at most 100 entries. Each entry follows the Mac `MarketListing` shape: `id`, `title`, `summary`, `capabilityId`, `version`, `packageSpec`, `installable`, and `requirements`. Every entry must have `installable: false`. `requirements.signature` must be `{ kind: "publisher", publisher, value }`, with an Ed25519 signature over the Mac catalog's `declarationBytes` payload. Configure `marketPublisherKeys` as a map from publisher ID to base64 SPKI DER public key. The server verifies every signature and rejects the entire file when one entry is invalid. Unknown fields, including price fields, are rejected. Keep signing private keys outside the host configuration and catalogue file.

For Mac API mode, set `connection: "api"`, `apiBaseUrl: "https://<Guangzhou host>/qianshou-market/"`, and the same trusted `publisherKeys` in the Mac `qianshou-plugin-catalog` configuration. The trailing slash matters: the Mac client resolves `plugins` against this base URL. The external reverse proxy must forward `/qianshou-market/plugins` to the DSH `webServer`; this repository does not configure that proxy. The Mac client validates the response and signatures again. It sends no browser credentials.

This directory describes reviewed metadata only. There is no approved product catalogue in the source tree, and this endpoint does not certify installation, local execution, pricing, purchases, publisher submission, or task supply. A future write path needs product review, executable capability verification, purchase/entitlement records, and device owner consent before any entry can become installable.

### Signed release metadata candidate

The separate, read-only `GET /qianshou-market/releases` endpoint returns `{ "releases": [] }` until `marketReleaseRegistryPath` is configured. A configured release also needs `marketArtifactDir`, `marketPublisherKeys`, and `marketOperatorKeys`. Every entry is fixed at `installable: false`. The server checks each configured release as follows:

- `pluginId + version` and `releaseId` must be unique. OS/architecture, operation/capability IDs, executor kind, schema hashes, permissions, package size, and SHA-256 are signed.
- The publisher signs the release with Ed25519; an independent review operator signs the same release and publisher proof. A claim that a version is merely “signed” does not pass.
- `marketArtifactDir/<packageSha256>.qspkg` must be a regular file whose size and full SHA-256 match. A symlink, missing or changed package, or invalid signature rejects the complete registry with 503. Archives reside in a `0700` directory as `0600` files, and the registry must not be group/other writable. The limits are 512 MiB per archive, 1 GiB total artifacts, 1 MiB registry, and 100 releases. The server rehashes an archive when its inode, size, modification time, or change time differs from the last verified snapshot.
- A `0600` version lock beside the registry (or at `marketReleaseLockPath`) prevents a previously served version from changing or disappearing across process restarts. Back up that lock with the registry and verify its restore before deployment.

The response includes server-owned `verificationScope: "opaque-archive-bytes"`: the generic release reader proves raw archive bytes and signatures; its metadata does not certify ZIP entries or execution. The declared permissions are restricted to compute-core's five manifest permissions, but operations still need a matching client adapter and trial. An isolated client may use `marketArtifactAccessToken` as a private preview bearer. This static preview token is not a purchase license and must not be bundled in a consumer build. The metadata route remains public and every release remains `installable: false`. Keep signing private keys outside the server. Before public deployment, capacity-test and rate-limit the route, verify multi-instance lock consistency, and verify reverse-proxy routing. Run `node --experimental-strip-types --test packages/host/model-gateway/tests/plugin-releases.node-test.mjs` for focused HTTP and integrity checks.

### First free seed package

`POST /api/qianshou/ai/plugins/submissions` is a server-authenticated carrier with `submit`, `mine`, `pending`, `approve`, `approve-declaration`, and `reject` actions. It is disabled without private `marketSubmissionStagingDir`, `marketReleaseRegistryPath`, `marketArtifactDir`, trusted Ed25519 public keys, and explicit `marketPublisherAccounts`/`marketOperatorAccounts` bindings from signing IDs to verified account IDs. A publisher submits an archive as base64 with `publisherId`, `title` and `summary`; the server records the verified account. The original exact five-file `qianshou.csv-profile` ZIP v1 remains the only format eligible for `approve`: the server rejects extra/traversal/symlink/bomb entries, checks raw input/output JSON Schema hashes, then rechecks the staged archive and every independently signed platform, architecture, operation, digest and permission before atomically appending the immutable release registry. Its reviewed Mac Host adapter is separately required. Private signing keys remain outside the service. No automatic approval, paid listing, installation, or task-intake authorization is implied.

The second accepted intake format, `qianshou.declaration.v1`, stores third-party **data-only declarations** for review. Its ZIP contains exactly `manifest.json`, `schemas/0/input.json`, `schemas/0/output.json`, through `schemas/N-1/input.json` and `schemas/N-1/output.json`, where `1 ≤ N ≤ 16`; ZIP entry order is unrestricted, and no script, binary, sample, extra file, or directory entry is accepted. The manifest has exactly `format`, `pluginId`, `version`, `releaseId`, `platforms`, `architectures`, and `operations`. Each indexed operation has exactly `capabilityId`, `operationId`, `executorKind`, `inputSchemaSha256`, `outputSchemaSha256`, and `permissions`. IDs, OS/architecture, executor (including tool, workflow and model) and permissions use bounded vocabularies; each capability/operation pair is unique. Schema digests are lowercase SHA-256 of the **raw** corresponding JSON bytes, and each schema is a JSON object with `type: "object"`. All generic JSON entries must be UTF-8 bytes equal to `JSON.stringify(JSON.parse(bytes))`, avoiding ambiguous duplicate keys and alternate encodings. The ZIP is limited to 2 MiB, each entry to 512 KiB, and total uncompressed bytes to 2 MiB; only ordinary UTF-8 named stored/deflated files with matching local/central metadata, CRC, no ZIP comments or extras, and contiguous entries pass. The `submit` request caps the JSON body at 3 MiB and base64 at 2,796,204 characters, enough to carry the 2 MiB archive ceiling. The returned `packageSha256` hashes the exact ZIP bytes; `unpackedTreeSha256` hashes `JSON.stringify([[path, sha256], ...])` in manifest-first index order, then input/output order for each operation. For a declaration, the executable-release `approve` action still returns `PLUGIN_REVIEW_UNSUPPORTED` (409). The separate `approve-declaration` action accepts only an independently signed metadata review. It rechecks the staged ZIP, account and key bindings, every archive and manifest digest, and conflicting decisions or versions before writing a private immutable review receipt. `mine` then returns `review.status: "declaration-reviewed"`, `scope: "declaration-only"`, and `installable: false`. No release registry entry, artifact download, license, sale, or dispatch is created. A reviewed declaration still needs independently verified executable code, safe adapter and runtime trial, and commercial policy before any installable release path can be added. Run `node --experimental-strip-types --test packages/host/model-gateway/tests/plugin-declaration-submissions.node-test.mjs packages/host/model-gateway/tests/plugin-seed-flow.node-test.mjs` for both formats.

The third intake format, `qianshou.reviewable-execution.v1`, is a single canonical UTF-8 JSON file, at most 256 KiB, containing a complete bounded declarative program. Guangzhou independently reparses every byte: 1–16 distinct operations, flat required string input/output schemas with at most 32 safe field names, canonical platform/architecture lists, byte/time limits, and only the `qianshou.string-map.v1` copy/trim/ASCII case-map instructions. It recomputes each implementation SHA-256 from the actual normalized program and each input/output Schema SHA-256; scripts, paths, constants, arbitrary permissions, unknown executors, noncanonical JSON, duplicate keys and unsupported fields fail intake. The submission record retains the full verified manifest and exact package digest; for this single JSON file, `unpackedTreeSha256` is SHA-256 of `JSON.stringify([["artifact.json", packageSha256]])`. No Mac-provided digest is accepted as proof.

An independent bound administrator may submit `{"action":"approve-execution","submissionId":"<UUID>","candidate":{...}}` on the internal authenticated submissions route. The candidate has `format: "qianshou.execution-release-candidate.v1"`, the verified submission/account/publisher and plugin/version identities, `releaseId: "execution." + full packageSha256`, title, summary, archive byte count and digests, `verificationScope: "self-contained-declarative-program"`, and every operation's ID, capability ID, executor kind, implementation/Schema digests, empty permission list and limits. It contains `publisher:{id,accountId,signature}` and `approval:{reviewId,operatorId,operatorAccountId,reviewedAt,signature}`; the publisher signs `pluginExecutionPublisherPayload(candidate)`, and the separate reviewer signs `pluginExecutionApprovalPayload(candidate)`. Both functions domain-separate and serialize fields in source-defined order. The server verifies both public keys, account bindings, reviewer independence and freshness, then reopens and independently verifies the staged program before atomically storing a private `0600` immutable candidate. `mine` returns `review.status: "execution-candidate-reviewed"`. Both signatures bind the exact package and every operation; altered or conflicting versions fail. The candidate is fixed at `installable:false`, `saleable:false`, `dispatchable:false` and does not enter the existing release registry, old CSV license ledger, public catalogue or artifact endpoint. A separate Mac runtime admission, public sale and dispatch policy remain future work.

The distinct `POST /qianshou-market/execution-access` route accepts only a request-bound Shanghai account Bearer and `{"action":"claim","submissionId":"<UUID>","packageSha256":"<64 lowercase hex>"}`. It rejects browser Origin/Cookie, cross-site requests, duplicate Authorization and bodies over 1024 bytes. Only the original submitting account can claim an independently reviewed candidate with that exact digest. A successful response contains `{ok,candidate,releaseId,pluginId,version,packageSha256,license,installable:false,saleable:false,dispatchable:false,download:{url,token,expiresAt}}`. `candidate` is the full publisher- and reviewer-signed object; the Mac Host must verify both retained public keys and every field itself. The private `0600` self-use license is idempotent and bound to `submissionId`, account, `releaseId` and package SHA-256; its `scope` is `self-use-review-candidate`. It is server-side access evidence, **not** an offline signed entitlement or an installable/commercial release. The random download token lasts five minutes; `GET /qianshou-market/execution-access?submission=<UUID>&sha256=<digest>` with `Authorization: Bearer <download token>` returns only the original canonical JSON after revalidating both candidate signatures, program implementation and license. The client must compare the response header `x-qianshou-package-sha256`, hash the downloaded bytes, independently reparse the program, and apply local owner authorization before any private execution. Never pass the download token through browser Remote or log it. The external proxy still needs explicit TLS routing and request limits; no deployment or Mac installation is established by this source. Run `node --experimental-strip-types --test packages/host/model-gateway/tests/plugin-reviewable-execution.node-test.mjs` for candidate, account and download checks.

Submission intake allows 1000 records **per verified account**. New uploads also pass a global staging guard of 50,000 files and 16 GiB of staged bytes. Reaching the account limit returns 429; the global storage limit returns 507. Neither limit hides existing `mine` history. `mine` and administrator-only `pending` return `{ok:true,submissions:[...],nextCursor:<UUID|null>}` with at most 20 items and an approximately 3 MiB item budget per page, below the Mac bridge's 4 MiB response cap. Send `{"action":"mine","cursor":"<previous nextCursor>"}` until `nextCursor` is null; a cursor outside that account's ordered list returns 400. Sorting uses descending `submittedAt`, then descending `submissionId`. Callers must cap total pages and deduplicate if concurrent submissions arrive between pages.

The Mac Host can use a separate `POST /qianshou-market/submissions` route with its Shanghai account Bearer. The public bridge accepts only `{"action":"submit","publisherId":"...","title":"...","summary":"...","archiveBase64":"..."}` and `{"action":"mine"}`; `pending`, `approve`, `approve-declaration`, `approve-execution` and `reject` return 403 before the intake handler runs. It rejects browser Origin/Cookie, cross-site fetches, duplicate or malformed Authorization, encoded bodies and requests over 3 MiB; it forwards only the one Bearer header to a request-bound verifier. Every request is checked against `/api/v8/auth/me` at the fixed `marketLicenseAccountApiOrigin`. No Guangzhou process-wide browser session is used for this path. The existing `/api/.../submissions` browser route remains separate. Missing or revoked identity returns 401; missing account verification configuration or upstream failure returns 503; an author ID not bound through `marketPublisherAccounts` and `marketPublisherKeys` returns 403. The route also requires the private staging, registry and artifact paths used by the intake handler. A successful submission returns the account-bound `submissionId`, exact archive `packageSha256`, manifest and `review.status` via paged `mine` requests. The bridge limits each response to 4 MiB; an oversized response returns 503 without truncating results. The current `submit` action has no idempotency key: after a timeout, compare paged `mine` with the local package digest before retrying, or duplicate submissions can be created. The external reverse proxy must explicitly forward this path and its Authorization header over TLS with rate limiting and token-free logs. Neither source nor loopback tests prove that the public route is deployed. Run `node --experimental-strip-types --test packages/host/model-gateway/tests/plugin-submission-bearer.node-test.mjs` for the HTTP loopback contract.

A reviewer approves declaration metadata with `{"action":"approve-declaration","submissionId":"<UUID>","review":{...}}`. The review contains exact `format: "qianshou.declaration-review.v1"`, submission/account/publisher IDs, plugin/version/release IDs, title, summary, ZIP and unpacked-tree SHA-256, byte count, `manifestSha256 = SHA256(UTF8(JSON.stringify(submission.manifest)))`, UUID review ID, operator ID/account, Unix-millisecond time, `scope: "declaration-only"`, `installable: false`, and a canonical Ed25519 signature. The reviewer signs `pluginDeclarationReviewPayload(review)` outside the service; this function prefixes `qianshou-plugin-declaration-review-v1\n` and serializes the listed fields in that order. The reviewer must be a current administrator bound to the signing key, and the time must be within five minutes of the server clock. Historic reads validate the retained key and stored submission without relying on the current operator-account binding. The `0600` receipt is published atomically and synced before acknowledgement; an identical retry succeeds, a different decision or colliding plugin version fails, and changed or unverifiable evidence returns an error. Back up receipt files with the staging directory. This is review evidence only, not the executable release or public product catalogue.

A reviewer rejects a submission with `{"action":"reject","submissionId":"<UUID>","rejection":{...}}`. The `rejection` object contains exactly `submissionId`, `packageSha256`, UUID `reviewId`, `operatorId`, `operatorAccountId`, Unix-millisecond `reviewedAt`, trimmed `note` (1–500 characters), and a base64 Ed25519 `signature`. Outside the service, the reviewer signs the UTF-8 bytes returned by `pluginRejectionPayload(rejection)`; that function domain-separates with `qianshou-plugin-rejection-v1` and serializes every other field in fixed order. At submission, the server checks the current administrator account and its `marketOperatorAccounts` binding, signature, submission ID, and archive digest; signing time must be within five minutes of server time. Historic reads use the signature and retained reviewer public key without depending on mutable administrator account bindings. Keep historic `marketOperatorKeys` when rebinding accounts; a revoked account cannot submit another decision. No private key enters service configuration. The service writes and syncs the complete receipt to a same-directory temporary file, publishes it as a private `0600` file through an atomic, no-overwrite hard link, and syncs the parent directory before its success response. If the link exists but directory sync fails, retrying the exact same signed receipt syncs again and returns success; a different receipt returns 409. A malformed submission ID returns 400, a valid missing ID returns 404, and damaged or unverifiable files return 503. A residual `.tmp` file is not a decision; a modified final receipt fails verification. `mine` returns `review.status: "rejected"`, reason, and signature to the submitting account; `pending` excludes the item. Approval and rejection share the registry write lock: a rejected submission cannot later be approved, and an approved one cannot be rejected. Back up these receipts with the staging directory. This action does not change Shanghai's older marketplace review queue and remains an undeployed source candidate for the Guangzhou public service.

## Ordinary skill submission and staff publication

`marketOrdinarySkillStorePath` enables the existing gateway's separate `ordinary_skill` publication kind in a private `0600` SQLite index under an owned `0700` directory. It contains submissions, immutable package/price metadata and signed staff decisions, with no funds ledger. It reuses `marketLicenseAccountApiOrigin`, `marketOperatorKeys` (base64 SPKI DER Ed25519) and `marketOperatorAccounts`. `marketOfficialSkillAccounts` is the authority-maintained account allowlist for `publisher_kind:official`; absent membership returns user, without trusting author or reviewer claims. Ordinary users need a verified Shanghai account, without a prebound adapter publisher or executor/capability ABI. Existing adapter submissions, paid-order reviews and licenses retain their contracts.

The Mac Host uses `POST /qianshou-market/skills` with its request-bound Shanghai account Bearer. `submit` accepts exactly `{action,requestId:UUID,skillId,version,title,summary,price_yuan,archiveBase64}`; currency is CNY and the explicit price is a nonnegative decimal string with up to two fractional digits. Request IDs are account-bound and exact retries recover the same immutable submission; changing the bytes or price conflicts. A ZIP is bounded to 2 MiB compressed/unpacked, 128 regular files and 512 KiB per file, and contains one UTF-8 `SKILL.md` at root or one common top-level folder. Traversal, symlinks, overlapping ZIP records and case collisions are rejected. Inspection never runs instructions or scripts. Every projection includes the original requestId. Unknown submit responses recover only with `{action:'mine',requestId:UUID}`, scoped to the current owner and returning zero or one existing record; they do not resend the package. `mine` and `catalog` accept `{action,cursor?}` and return pages of 20 with `nextCursor`; `GET /qianshou-market/skills` returns the first public published page. Public POST blocks staff operations and browser carriers.

A mapped administrator uses the existing browser carrier `POST /api/qianshou/ai/skills/submissions`: `pending` lists the queue, and `{action:'pull',submissionId}` returns the original archiveBase64 and SHA for employee testing. After the employee manually tests those exact bytes, `{action:'review',submissionId,review:{key_id,payload,signature}}` records an independent signed publish/reject decision. Payload fields are exactly `{schema:'qianshou.ordinary-skill-review.v1',purpose:'qianshou:ordinary-skill-review',submissionId,accountId,skillId,version,title,summary,price_yuan,currency,packageSha256,packageBytes,unpackedTreeSha256,skillMdSha256,skillMdPath,manual_test:{tested,test_receipt_sha256},decision:'publish'|'reject',note,reviewId,operatorId,operatorAccountId,reviewedAt}`. The external employee key signs `ordinarySkillReviewBytes(payload)` (sorted-key canonical JSON); the signature is canonical base64. New decisions require the mapped current staff account, independent from the author, and a timestamp within five minutes. Publish requires `tested:true` and the actual manual test receipt SHA. The service reopens and verifies the original archive, binds the requested price, rejects same-version replacement, persists before confirming, and accepts only identical review retries. Private signing keys stay outside the service.

Only manually published ordinary skills enter this catalog. ## Non-billable research tasks

Research uses independent `researchDirectoryCredentialRef` (read-only metadata) and `researchDispatchCredentialRef` (same-account tasks). These credential references cannot reuse formal dispatch, exchange or metadata references. No formal profile, worker qualification, quote or balance is required. The fixed Qwen workflow `comfy-pilot-image-154f7d6133fe0276` accepts only `{prompt}` and produces 2048×1152 PNG at 8 steps. A probe can confirm only the originally reported model and workflow; newly learned hashes or versions may refine empty fields. Other discovered APIs remain visible but are unavailable to this fixed trial dispatcher. A confirmed API does not establish current idle resources.

Device Bearer POST `/v1/nodes/research/execution` accepts exactly `{deviceId,connectionEpoch,observationRevision,mode:'image',idle:boolean|null,resourceAllowed:boolean|null}`. The server binds the current registered API revision, stamps `observedAt`, and returns exactly `{ok:true,deviceId,connectionEpoch,observationRevision,mode:'image',observedAt}`. The optional read-directory `execution` has eight fields: `schema:'qianshou.research-node-execution.v1',observedAt,connectionEpoch,observationRevision,idle,resourceAllowed,activeTasks,slotCount:1`. At 15 seconds, or after heartbeat/policy/revision/epoch invalidation, resource flags become unknown. `activeTasks` is the union of persisted unfinished research/formal attempts and heartbeat running ids. Nodes cannot report this count. Shanghai also reserves one slot per device before dispatch.

`POST /internal/media/research/dispatch` accepts an exact 14-field `qianshou.research-media-lease.v1` request and freezes the current API revision plus `non_billable:true`. SQLite checks and reserves the device atomically. A stale resource report returns `RESEARCH_EXECUTION_NOT_READY` before insertion. An unknown result retains the original task/attempt and occupancy after lease expiry or reconnection. `/internal/media/research/task` reads that original tuple. `/v1/nodes/research/channel`, `/claim`, `/events` and `/task-status` use a separate cursor and current device credential. A persisted duplicate claim reconciles the original submission; it cannot authorize another model POST. Resource withdrawal prevents a new claim while the original claimed job can continue GET recovery and delivery. The Host still performs its final idle and owner-policy check immediately before its sole runtime POST. See [the reservation decision](../../../.agents/notes/2026-09-30-research-node-capacity.md).

PNG bytes travel node→Guangzhou→account, never through Shanghai. `/v1/nodes/research/results/upload` accepts at most 64 MiB and verifies complete PNG chunks, CRC, dimensions and SHA before an immutable original file can complete the task. Account Bearer GET `/v1/media/research/result?taskId=<UUID>&attemptId=<UUID>` reads only the original account-bound artifact; no formal viewer grant or service credential is sent to the PC. Download failures retry this GET only, never regenerate. No research completion creates a charge or settlement receipt.

`POST /v1/nodes/device-info` accepts device Bearer and exactly `{deviceId,connectionEpoch,deviceInfo}`. Device info contains `os,osVersion,arch,deviceName,cpu,gpu,memoryMb,vramMb`; labels exclude paths, endpoints, IPs and control characters. GPU unified memory has `vramMb:null`. Missing evidence remains null and is not a hardware qualification. Administrator projections include optional `username` and `deviceInfo`; research-directory responses do not include them. Username comes only from Shanghai `/api/v8/auth/me` during registration or account Bearer POST `/v1/nodes/account-identity` with exactly `{deviceId}`. Refresh verifies the original owner and changes neither device epoch nor authorization.
