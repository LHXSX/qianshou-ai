# 设计说明 · 千手 AI 运营管理台

> 这份文档回答三个问题：**这是个什么东西**、**权限模型是怎么落地的**、 **哪些能力现在是真的、哪些还在等别人**。代码位置：`packages/host/admin-console`（服务端）、 `apps/qianshou-admin`（前端）、`deploy/admin-console`（部署）。

## 一、定位与硬边界

它是**AI 产品的业务运营后台**（账号额度、订阅档位、技能市场、发现页、订单工单、权限审计）， 不是内容 CMS，也**不是**算力运营台。

| | 算力运营台 | 本管理台 |
| --- | --- | --- |
| 域名 | `qianshousuanli.com/eco-admin/` | `admin.qianshousuanli.com` |
| 管什么 | 节点、调度、经济、反作弊、商务、广告线索（32 页，只读） | AI 产品的账号/订阅/市场/内容/订单/权限 |
| 给谁用 | 现在内部；**后期要给非 AI 的企业客户** | 千手自己的运营/财务/客服/审计 |
| 前端工程 | 既有 Vue 工程 | **独立工程 `apps/qianshou-admin`**（从零建，不复用任何一行） |
| 角色表 | `surface: 'compute'` | `surface: 'ai-admin'`，**两边不互通** |

角色表分开不是口号，有三处执行点：

1. 写授权时 `roleGrantable()` 拒绝任何 `surface !== 'ai-admin'` 的角色（前端拿到 400 + 原因）；
2. 读 `roles.json` 时把面不对的角色**直接丢弃**（有人手工拷过来也不生效）；
3. 单元测试钉住"算力台角色不能被授予""内置角色面都标成 ai-admin"。

## 二、部署形状

```text
浏览器 ──HTTPS──▶ nginx (admin.qianshousuanli.com, 443)
                   │  只把真实来源写进 X-Real-IP
                   ▼
            qianshou-admin-console  (127.0.0.1:7090, 独立 systemd 服务)
                   ├─ 静态：/srv/qianshou-admin/web        （Vue 产物）
                   ├─ 接口：/api/qianshou/ai/admin/*       （本服务）
                   ├─ 数据：/srv/qianshou-admin/data       （admins/roles/whitelist/flags/audit）
                   ├─ 只读：/srv/qianshou-home/*.json      （账本快照、订阅快照）
                   └─ 上游：https://qianshousuanli.com/api/v8  （账号体系：登录/身份核验）
```

刻意**独立**的理由：管理台要能在工作台挂掉时仍然可登录（否则出事时连审计都查不了）、 要能单独重启/升级/限流、要能单独限 IP。它与 `qianshou-workbench` 没有进程内耦合。

## 三、请求流水线（顺序不能换）

```
① 来源地址  →  ② IP 白名单  →  ③ 同源检查  →  ④ 会话  →  ⑤ 权限  →  ⑥ 二次确认  →  ⑦ 审计
```

1. **来源地址**（`client-ip.ts`）：只有 socket 对端是回环时才采信 `X-Real-IP`。 非回环连接（将来若直接暴露端口）一律用 socket 地址——客户端伪造的头被完全忽略。 2. **IP 白名单**（`whitelist.ts`）：默认拒绝；回环永远放行（逃生路径）；被拒也写审计。 每次请求比对文件指纹，**CLI 在另一个进程里加白名单会立刻生效**（不需要重启）。 3. **同源检查**（`http.ts`）：带 `Origin`/`Referer` 的请求必须等于本站源。 4. **会话**（`session.ts`）：cookie 里的随机串 → 内存会话 → 管理员记录 → 角色。 定期（默认 10 分钟）向上游 `/auth/me` 核验；上游明确拒绝就**立刻吊销**， 网络故障则保留会话（不把一次抖动变成"管理员被踢出去"）。 5. **权限**（`server.ts` 的 `route()`）：每条路由声明权限键； **声明了权限校验但没给权限键的路由会在启动时抛错**（fail-closed 的落点）。 6. **二次确认**（`confirm.ts`）：高危操作分 preflight / apply 两步， 令牌 60 秒有效、一次性、绑定"同一个人 + 同一个动作 + 同一份载荷哈希"。 7. **审计**（`audit.ts`）：写操作、被拒的越权尝试、白名单拒绝、登录成功/失败全部只追加留痕， 写操作带 `before → after` 逐字段差异；口令/令牌/cookie 入库前遮盖。

## 四、权限模型的五条规则与落地位置

| 用户要求的规则 | 落地 | 测试 |
| --- | --- | --- |
| 角色 → 菜单权限 | `menuFor(role)` 在服务端过滤，`/session/me` 返回过滤后的菜单；前端只渲染 | `tests/rbac.spec.ts` 规则 1 |
| 角色 → 接口权限（**服务端强制**） | 每条路由声明 `permission`，`can(role, permission)` 判定；未知权限键一律不通过 | 规则 2 + `tests/server.spec.ts`（客服调权限管理接口拿 403） |
| 数据范围（自己 / 全部） | 管理员记录带 `scope`（个人覆盖），否则用角色的 `scopeDefault`；查询在**服务端裁剪** | 规则 3 + 集成测试"self 看不到别人的审计详情" |
| 高危操作二次确认 + 留痕 | `isHighRisk()` 来自权限目录；preflight/apply + `before → after` | 规则 4 + 集成测试（缺令牌 409、载荷不一致 409） |
| 与算力台权限彻底分离 | `surface` 三处执行点 | 规则 5 + 集成测试（磁盘里塞 compute 角色也不生效） |

权限目录（22 个权限点）覆盖六个业务模块 + 权限/审计/白名单/开关，见 `src/rbac.ts` 的 `PERMISSIONS`。内置角色五个：`super-admin` / `ops` / `finance` / `support` / `auditor`； 自定义角色可自由组合，**内置角色的权限不可改**（要别的组合就新建）。

## 五、管理员身份：为什么这样设计

**复用既有账号体系**（用户明确要求）：

- 登录 = 调用上游 `/api/v8/auth/login`（与手机端/电脑端同一个账号、同一份口令、同一套 TOTP）；
- 本服务**不签发账号**、**不落盘口令**、**不落盘上游令牌**（令牌只留进程内存）；
- 管理台自己的会话 cookie 是一个不透明随机串，服务端只存它的 `sha256`； **进程重启 = 所有管理台会话失效**（宁可重新登录，也不留长期凭据）。

**授权独立于账号**：账号存在 ≠ 能进管理台。授权表 `admins.json` 记录 `accountId → 角色 + 数据范围 + 是否启用`，由超级管理员在界面里或服务器上用 CLI 维护。

为什么这样分：

| 选择 | 不这么做的后果 |
| --- | --- |
| 管理台有自己的角色表 | 复用上游 `role`（`personal/pro/enterprise/admin`）会让"平台角色"和"运营权限"混成一件事：给某人升 `enterprise` 就顺手把运营权限给了 |
| 角色表与算力台分开 | 算力台后期要开给非 AI 企业客户，一个角色能同时进两个面，等于把 AI 运营权限暴露给客户 |
| 会话只在内存 | 落盘就等于"读走文件 = 拿到一个还能用的管理台会话" |

登录的三种失败**必须分开**（这是既有代码踩过的坑）：口令错 `401 invalid_credentials`、 账号对但没有授权 `403 not_an_admin`、上游不可达 `502 upstream_unavailable`。 把网络抖动说成"请重新登录"会把人引向错误的动作；这三种都在集成测试里钉住。

## 六、数据来源与就绪度（不造假数据）

| 模块 | 状态 | 数据从哪来 |
| --- | --- | --- |
| 账号与额度 | `read-only` | 直接读工作台的账本快照 `.qianshou-ledger.json`（授予/已用/预留/逐次流水） |
| 订阅与档位 | `read-only` | 直接读订阅快照 `.qianshou-subscriptions.json`；档位目录动态读模型网关的 `tiers.ts`（**唯一来源**，不抄一份） |
| 技能 / 专家市场 | `dependency-unavailable` | 占位页：缺市场目录服务（列出需要的 4 个接口） |
| 发现页内容 | `dependency-unavailable` | 占位页：缺内容服务（列出需要的 4 个接口） |
| 订单与工单 | `dependency-unavailable` | 占位页：缺交易/工单服务（列出需要的 4 个接口） |
| 权限与审计 | `ready` | 本服务自己的数据 |
| IP 白名单 | `ready` | 本服务自己的数据 |
| 功能开关 | `ready` | 本服务自己的数据 |

**写操作为什么都是"依赖未就绪"**：账本与订阅的属主是工作台进程（内存态 + 结算逻辑）。 外部直接改文件不会生效——下一次结算就会覆盖，而用户会以为钱已经退了。 所以"处理异常扣费""开通订阅"如实返回 `503 dependency_unavailable` 并列出需要的接口， 而不是做一个看起来能用的假动作。接口调用本身仍然过权限校验并写审计。

## 七、IP 白名单与逃生路径

- **默认拒绝一切**：白名单为空 = 只有本机回环能进；
- **回环永远放行**：这是逃生路径，也是第一个管理员的创建路径；
- **两层同时生效**：服务端在**任何**请求（SPA 资源和接口）之前判定，所以"挡了接口没挡页面" 这种半吊子状态不存在； - **唯一事实来源**：nginx 层不复制一份 allow/deny（两份规则必然漂移， 漂移的表现是"页面进得去、接口 403"）；vhost 里留了可选的注释块备查； - **CLI**：`whitelist add/remove/enable/disable`，改动对运行中的进程立刻生效； - **自锁保护**：界面里删掉"正在放行自己的那条规则"会被拒（除服从回环操作时）。

## 八、关键取舍记录

| 决定 | 理由 |
| --- | --- |
| 自建管理台，不引 Payload/Strapi/Directus | 用户已拍板；而且这些 CMS 的权限模型是"后台管理员 + 角色"，与本项目"两套角色表分离 + 数据范围 + 两步确认"的形状不同，改造成本高于自建 |
| 服务端不用外部依赖（只 `node:http`/`fs`/`crypto`） | 部署到服务器时不需要在服务器上装依赖或构建；Node 22.23 直接跑 TS（类型剥离），"线上跑的就是测试跑的那份源码" |
| 前端独立 Vue 工程 | 与算力台同栈、但工程独立（用户要求）；不复用算力台的任何路由/权限表 |
| 审计用 JSONL 只追加 | 快照形态允许"读出来改一改再写回去"，那正好是审计最不该有的性质 |
| 每一步都要有测试 | 用户要求"逐条可测"；`tests/` 下 105 个用例覆盖白名单、权限五规则、审计、确认令牌、会话与端到端链路 |

## 九、已知限制（不藏的）

1. **管理台自己的口令/2FA 策略没有叠加**：登录强度等于上游账号体系的强度。 要更强（比如强制管理台 2FA）需要在授权表上加字段并接 TOTP 校验。 2. **会话不落盘**：进程重启需要重新登录（这是有意的权衡，不是缺陷）。 3. **数据范围 `self` 目前作用在审计/账号/订阅列表**：等订单与工单服务建好后要接上同一套裁剪。 4. **审计文件单文件增长**：超过 32 MiB 时查询只读尾部（有 `truncated` 标记）。轮转与归档未做。 5. **上游账号服务的"账号可用性"依赖实时调用**：上游长时间不可达时，登录会 502（会话保留但无法新建）。
