# Shanghai CNY payment candidate

This candidate extends the existing `we_payment_orders → mark_paid → deposit → we_ledger` path. It does not define Guangzhou SP conversion, subscription grants, fees, refunds, or bank reconciliation policy. See `README.zh.md` for the full API and configuration reference.

WeChat uses API v3 **Native QR**, returning `payment: {mode: "wechat_native", code_url}`. Alipay uses RSA2 **`alipay.trade.page.pay`** (电脑网站支付, a page-jump cashier), returning `payment: {mode: "alipay_page", action, method, params}`; the server only signs and the browser submits the parameter set, so no HTML is ever returned and there is no server-side response to verify. `alipay.trade.precreate` (`payment: {mode: "alipay_precreate", qr_code}`) is retained for the 当面付 product, which this merchant has **not** signed — only 电脑网站支付 is enabled, and that product's `precreate` is absent from the enabled API list. Neither path fabricates a JSAPI `prepay_id`. Only authenticated provider responses produce payment instructions. Prepayment itself never credits funds.

Gateway responses are **not UTF-8**. Measured against the live gateway with a read-only `alipay.trade.query`: it answered `Content-Type: text/html;charset=GBK` with GBK bytes even though the request asked for utf-8, and the `sign` is computed over the GBK bytes (the same slice re-encoded as utf-8 does not verify). `_verified_response()` therefore decodes with the declared charset and re-encodes the signed slice with **the same codec**. Before that fix it reported "Invalid provider JSON" for every real response containing non-ASCII — which mocked UTF-8 test bodies can never catch. Async notifications are unaffected: the body is URL-encoded ASCII with the charset carried inside it, and we require `charset=utf-8`.

`alipay.trade.query` is implemented as the reconciliation path the official documentation names as authoritative when a notification is missed. A standalone command reports mismatches and credits nothing unless `--apply` is given:

```bash
python -m platform_v8.services.payment.reconcile_orders
python -m platform_v8.services.payment.reconcile_orders --apply
```

It classifies each recent order as `in_sync`, `provider_paid_local_unpaid`, `amount_mismatch`, `tx_mismatch`, `provider_has_no_order`, `local_paid_provider_unpaid` or `query_failed`. Only `provider_paid_local_unpaid` is creditable, and only through the existing `mark_paid` writer, so the order lock, amount/currency/gateway cross-check and idempotent ledger key all still apply. A bad signature is never downgraded to "unknown". The query response does not echo `passback_params`, so a query-driven credit takes the binding from our own row — which was located by the signed `out_trade_no` — while the authoritative facts (`out_trade_no`, `trade_status`, `total_amount`) come from the signed response.

All online money is CNY yuan with exact cent precision, positive and at most 1,000,000. WeChat receives integer cents; Alipay receives a two-decimal yuan string. Server-generated account bindings are echoed in signed notifications and compared against the locked local order. Provider/app/merchant/order/account/amount/currency/transaction mismatches reject without deposit. Invalid signatures return HTTP 400; missing credentials return 503 before a recharge order is created.

The existing ledger implementation already participates in its caller's transaction. This candidate preserves that boundary and adds strict paid-retry comparison, per-provider transaction advisory locks across orders, payment-writer account row locks, persisted ledger-ID lookup, and atomic successful-payment audit. It does not claim a global fix for every other ledger writer. The current gateway transaction index remains non-unique; all online payment writers must use the guarded service. Delayed verified success can credit a locally expired order. Manual/bank requests and the confirm body remain compatible; online orders require verified callbacks.

An uncertain provider request keeps its durable pending `order_no` and a requested/unknown audit trail. HTTP 502 includes that number. A user may explicitly retry `POST /api/v8/payment/orders/{order_no}/payment`; the same provider order number is reused. Do not automatically create another recharge. If the entire HTTP response was lost, inspect the user's order history; this implementation does not promise client-key-based recovery. Order GET endpoints report local state, not a live provider reconciliation query.

Public notification endpoints are `/api/v8/payment/notify/wechat_pay` (204 after commit) and `/notify/alipay` (200 plain `success`). Rejection logs contain only provider, processing stage, and an already verified order identifier, not callback bodies or credentials. Existing user/admin authentication dependencies remain in force for other endpoints. The new admin global list supports `limit`, `offset`, `account_id`, `status`, and `gateway`; its `total` counts all filtered rows. `OrderOut` adds `account_id`; `AdminOrderOut` also includes `ledger_id`.

Both channels default to disabled. Configuration uses `V8_PAYMENT_PUBLIC_ORIGIN` and the `V8_WECHAT_PAY_*` / `V8_ALIPAY_*` names documented in the Chinese reference. Private keys and API v3 key material must live in protected absolute-path files outside the repository. RSA keys must be at least 2048 bits. The current implementation pins one WeChat platform verification key/certificate; overlapping rotation still requires an operational design and validation before production use. Configured does not mean merchant-product approval or live acceptance has been verified.

The original expiry helper had no caller. A standalone command now defaults to dry-run:

```bash
python -m platform_v8.services.payment.expire_orders
python -m platform_v8.services.payment.expire_orders --apply
```

It uses the existing database configuration and changes no schema. The accompanying systemd service/timer files are inactive deployment candidates. They require a separately protected `/etc/qianshou/payment-expiry.env` and a verified runtime/database access path. No production timer was installed or enabled.

146 local tests exercise generated test certificates, real RSA2/SHA256 verification and AES-GCM, HTTP routes, an isolated PostgreSQL instance, transaction rollback, duplicate/concurrent callbacks, manual regression, permissions, uncertain prepayment, the page-jump cashier, the reconciliation command, and the actual expiry/reconcile commands in a temporary database. Cashier signatures are checked by an independently written verifier rather than the production helper, and that verifier is itself shown to reject tampered input. Ten mutations were detected and the source restored by SHA: dropping the RSA2 sort, using a wrong `product_code`, leaking an undocumented `seller_id` into `biz_content`, crediting despite an amount mismatch, and crediting when the provider says the trade is unpaid. Outbound payment traffic is intercepted by a test transport; no live payment or production database was touched.

The local Python 3.14 environment differs from the observed production Python 3.10.12 stack (FastAPI 0.110.0, Pydantic 2.6.4, SQLAlchemy 2.0.29, cryptography 42.0.5, httpx 0.27.2). Certificate UTC properties were checked on that server runtime, and new Python syntax is checked against Python 3.10; full server-runtime execution remains a separate isolated-candidate check. Live merchant credentials, provider reconciliation against a real merchant, key rotation, production callbacks, expiry activation, deployment/rollback, and real payment acceptance are not claimed complete.

Primary protocol references: [WeChat Native](https://pay.wechatpay.cn/doc/v3/merchant/4012791877), [WeChat notification](https://pay.wechatpay.cn/doc/v3/merchant/4012791861), [电脑网站支付 quick start](https://opendocs.alipay.com/open/00dn7k) and its [page.pay interface spec](https://opendocs.alipay.com/open/028r8t), [Alipay identity/amount checks](https://developer.alibaba.com/docs/doc.htm?articleId=105302&docType=1&treeId=204), [Alipay precreate](https://developer.alibaba.com/docs/api.htm?apiId=862&docType=4), and the [official Alipay SDK](https://github.com/alipay/alipay-sdk-python-all) — the enabled-field list for `biz_content` was read from that SDK's `AlipayTradePagePayModel`, which is why `passback_params`/`time_expire` are sent and `seller_id` is not.
