# 创建千手技能

1. 根据用户已有信息列出目标、何时调用、所需输入、输出格式和边界。缺少会影响实际执行的信息时，一轮只问最关键的 1–3 个问题；不要重复询问已知事实。用户只输入“我想创建一个技能或插件：”时，先询问要封装的重复任务和一次理想结果。
2. 看清这属于指令型技能还是需要运行代码或外部服务的插件。技能只能规定模型如何工作；若任务依赖尚未接入的 API、模型、账号或插件，明确列为依赖，不能声称草稿本身会带来能力。
3. 起草完整 `SKILL.md`。frontmatter 包含短的 kebab-case `name`、简短中文 `description`，以及 `metadata.displayName`（给机主看的中文短名）和 `metadata.category`（分类键）。分类键从 `text` 文案、`image` 图片、`video` 视频、`ppt` PPT、`spreadsheet` 表格、`research` 调研、`development` 开发、`automation` 自动化、`design` 设计、`data` 数据、`other` 其他中选最贴近的一个。正文只写改变实际执行决策的步骤、输出和边界；缺失的业务规则标为待确认。
4. 在完成前展示建议的中文名称、命令名和分类，提醒用户可改名；用户已经指定名称时沿用，不重复询问。展示可审阅的草稿并接受修改。仅咨询或索要草稿时不写文件。
5. 用户要求“创建／做好／保存／安装技能”即授权写入本机技能。先调用 `qianshou_skill_authoring_template` 并传已知英文命令名，从 `authoringContext` 读取当前 Host 实际用户根、`destination` 和同名冲突；不猜 `$DSH_HOME`，不搜索扫描或 watcher 源码。明确指定项目范围才写项目 `.agents/skills/<name>/SKILL.md`，否则沿用回执的用户目标目录和 `source`。存在同名文件时不能静默覆盖。辅助脚本、示例或视频文件不等于技能；必须真正写出 `SKILL.md` 才能说技能已创建。
6. 写入后重新读取 `SKILL.md` 核对名称和内容，并在当前会话通过技能目录或 `skill` 工具核对新技能是否被发现。结束时报告中文名称、命令名、分类及保存路径，提醒机主可在“我的能力 → 我的技能”和输入框技能菜单查看；只有目录回执证实后才说当前会话已经可用，否则说明文件已写入但会话加载尚待刷新。
7. 用户要的是可运行功能时加载同预设的 `plugin-author` 技能，按模板生成执行器、输入输出合同与至少两份不同的自检样例，然后直接调用 `qianshou_try_local_skill` 真实试用；通用运行包无需安装原生插件。固定的文本统计/反转代码只是示例；其他需求通过编写和测试真实业务代码完成。用户说“发布接单技能”时继续准备发布所需任务适配与核验资料，并以平台真实受理、审核、上架回执为准。

保存真实文件后调用 `qianshou_skill_complete`，传模板的 `source` 和保存名称。Host 核对文件并在原对话显示立即试用与发布操作；文件保存不能推断平台审核或可接单。
