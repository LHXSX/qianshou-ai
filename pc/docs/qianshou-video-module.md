# Qianshou video module: creation for ordinary users and heterogeneous node intake

English | [中文](qianshou-video-module.zh.md)

Video belongs in one product module, not in a separate channel for every computer or skill. Buyers use one `@出视频` entry. Behind it, a versioned `video.render` task contract selects a reviewed workflow, compatible node and price. Nodes may run different operating systems, models and hardware; H3 on the initial 5080 is an acceptance example, not the architecture. Every order pins a publication ID, contract digest and resource limits. Shanghai handles review, pricing, orders and scheduling metadata only; first-frame and MP4 bytes move through Guangzhou object storage and execution nodes.

A first-time PC user should be able to sign in, chat and complete basic tasks. When a specialized video or design capability is needed, its module explains what it can do, required materials, estimated cost and output. A node owner sees which capabilities their device can offer, what is missing, whether intake is enabled, and orders and earnings. Understanding JSON, ComfyUI graphs or server topology is not a prerequisite for either person. Advanced setup may be available on demand.

## Buyer: three ordinary steps with optional advanced controls

1. **Describe the idea.** Use one sentence, such as “a little white cat runs toward the camera across grass in a five-second clip.” Keep the original description visible; do not imply that an AI has already understood the visual content.
2. **Fill only real gaps.** Ask about missing details that change the result: subject and action, purpose or aspect ratio, and first-frame source. Do not repeat details already stated. Prefill length, aspect ratio or sound only when the current reviewed contract supports those values; otherwise show the available range. Optional details can be skipped, and the ordinary path should fit on one screen.
3. **Confirm, then run.** Show the final description, selected real first frame and source, supported duration and aspect ratio, actual per-run CNY quote, and a defensible wait estimate. Creative approval permits upload of only the selected image snapshot. The user separately approves the server quote before a paid order. Deliver a playable MP4 card and download in the conversation, with a useful failure reason rather than a disk path alone.

First-frame choices are “Use my image,” “Find an image on this computer,” and “Generate one for me.” The first two show only real, readable local files with previews. The third requires a separately available image provider and its own quote; a decorative picture is not a generated candidate. A text-to-video contract may allow skipping the first frame, but an H3 recipe that requires one must say so and block ordering without it. Browsing and choosing images uploads no media before confirmation.

Advanced controls stay inside the same module: camera movement, composition, style, negative constraints, seed, first and last frames, or a storyboard. Show only fields and ranges that the selected reviewed contract declares, along with price effects. Extra natural language may be organized into the description; it must not become arbitrary Comfy JSON, local paths or unreviewed parameters. Simple and advanced flows produce the same order contract.

## Node: installation, self-test, review and intake are distinct states

Before an owner offers video work, the PC runs a read-only preflight against the selected reviewed recipe: hardware headroom, driver, execution service, model and plugin roles, workflow digest, encoder, output space, and current account and device binding. Only an H3 recipe requires ComfyUI, H3's five model roles and its fixed four-step workflow. Other recipes are checked against their own manifests. Show ready, missing, version mismatch or unknown for each item. Unknown is not ready, and a model filename alone does not establish usable model bytes.

For a missing component, show download size, source, license and expected disk space. The owner confirms any download. Download only a platform-reviewed version manifest, resume safely and verify complete content hashes. Keep model and workflow files in a node-private location; buyer materials, model files and absolute paths do not go to Shanghai. Reuse an existing component when it verifies. Different GPUs and models may use different reviewed recipes rather than requiring code changes for each Windows machine.

Installation permits local trial only. Two independent five-second samples then check a pinned image, real model and plugin files, GPU execution, one MP4, full-frame decoding and output SHA. Passing allows a local skill draft. Publication still needs platform review of version, source, price and independent result acceptance; the owner then separately enables intake. Any model, workflow or artifact digest change invalidates the old self-test. An old green indicator cannot survive a changed installation.

## Per-order identity that cannot be omitted

- The buyer chooses an available reviewed publication from the live catalog. If `@出视频` can use several different contracts, ask which one to use rather than switching silently.
- Quote and task creation bind publication ID, artifact and contract digests, first-frame object bucket/key/version/SHA/size/MIME, description and parameters. Re-read review status and actual price before ordering; a change requires new confirmation.
- Before GPU reservation and before Comfy `/prompt`, Windows checks the signed assignment, installed device, current review, versioned first-frame bytes and durable once-only reservation. An unknown `/prompt` outcome is not automatically retried. Accept only the unique MP4 under this attempt's output prefix.
- Windows uploads the MP4 as a pinned object version. Guangzhou independently reads and fully decodes it, checks the order and object lock, then signs a result receipt. Shanghai does not download or accept the video bytes. Mac shows the playable deliverable from a Guangzhou-authorized media address.

## Acceptance standard

“Publishable” requires a real public video contract and review, a once-only ledger verified on Windows NTFS, versioned input download, streaming MP4 upload beyond the old small-file limit, Guangzhou HTTP acceptance and signed receipt, and one real buyer flow: confirmed quote, Shanghai assignment, Windows GPU execution, Guangzhou video validation, and Mac playback. A source build, local sample, catalog card or unit test alone is not market intake acceptance.

Current candidate source includes a buyer natural-language flow and local first-frame recommendations, reviewed-publication binding, a default-off Windows Comfy consumer, isolated Shanghai patches and an independent Guangzhou video checker. The real cross-machine market loop above has not passed acceptance. The older fixed H3 sample is device-test evidence, not a generic video-module order result.

## Three film strategies share one video project

Buyers always enter through `@出视频`. Both easy creation and professional creation use conversation to fill gaps; neither exposes JSON, device setup or node graphs as buyer requirements. Easy creation asks only for missing details that change the work. Professional creation guides discussion of story, scenes, characters, storyboard, camera, sound, first frame and duration, and supports revision. An AI may draft a plan; creative approval precedes a project quote. One project quote must account for planned generation, separate image work, assembly and validation, with fresh approval for additional costs. A user may choose an execution strategy, or the system may recommend a reviewed available option, but neither model, price nor final duration may change silently.

1. **One-to-one short clip.** One reviewed video recipe creates one shot on a compatible node. Today's fixed five-second H3 graph is only one possible recipe. Show its supported length, resolution, first-frame and sound behavior. A one-minute request cannot be quoted as a five-second task; it enters long-film planning until an appropriate reviewed contract exists.
2. **One-to-one long film.** A project creates a script and storyboard, then divides work into numbered shots that can be verified and recovered independently. One compatible node makes them in sequence where appropriate; sound, subtitles, transitions and final assembly follow. A ten-minute film is not one unrecoverable GPU call. If the device goes offline, pause. Migration, when authorized, requires checking another node's recipe compatibility, asset rights, price and quality constraints.
3. **One-to-many distributed long film.** An approved project plan becomes a dependency graph. Shanghai allocates metadata and short leases using recipe version, open slots, VRAM, queue, deadline and quote. Independent shots may run on multiple compatible nodes. Shots depending on a predecessor's last frame, a character anchor or a continuous scene run in dependency order or as a grouped sequence. Dividing total duration evenly across N nodes is not enough. Different models do not automatically produce a coherent film; cross-model use needs reference assets and sample acceptance, or a compatible node cohort.

Distributed execution can reduce generation time but cannot promise linear acceleration. An hour of final footage divided into five-second shots is roughly 720 shots. With 100 nodes that are actually online and compatible with the same recipe, fully independent shots and one concurrent shot per node, pure generation has an ideal lower bound of about eight waves. A real estimate follows the critical path, shot-specific runtime, scene dependencies, memory and queue constraints, and node success rates, then adds script work, anchors, upload, per-shot validation, rework and assembly. Show the real number of eligible nodes, concurrently runnable shots and basis for an estimate. With no reliable measurement, show stages rather than a false “100× speedup” or exact finish time.

All three strategies share the identity chain `video project → shot plan → reviewed recipe and assets → node attempt → shot acceptance → assembly acceptance → delivered film`. Shanghai stores project, order, dependency, lease, budget and terminal-state metadata. Scripts, reference images, first and last frames, shot videos and final-film bytes remain in Guangzhou-authorized versioned storage or execution nodes, never relayed through Shanghai. Planning and the [image module](qianshou-image-module.md) are separate reviewed capabilities. Possible H3 image output does not make an unreviewed, unpriced image service available.

An hour-long film adds chapter and scene levels above shots. Conversation establishes audience, genre, characters, chapter count, target duration per chapter and budget before the script, relationships and video bible are drafted. The user reviews each chapter synopsis and storyboard and chooses system assignment or a specific creator or certified device. A selected device still has to meet recipe, load, rights and deadline rules. If it cannot, show the reason and alternatives rather than silently reassigning it. Produce a few key shots or inexpensive samples per chapter and pass character and style continuity checks before batch work. Chapters can run in parallel, but a shared-character asset change reopens dependent chapter approvals. Each chapter can supply rough cuts for feedback; a separately reviewed assembly task handles dialogue, music, subtitles, chapter transitions, titles and final acceptance.

## Video bible and recoverable shot plan

A video bible is not one universal reference image. It is a versioned, user-approved project package: character faces and clothing, settings and props, style and color, key references, camera language, voice and dialogue rules, allowed model and workflow versions, material rights, and explicit exclusions. Each shot receives only the versions it may use, its prompt, allowed duration, input and output obligations, and upstream-shot receipts. A node cannot rewrite the bible or fetch unrelated project material. When the bible or storyboard changes, affected shot quotes and results become stale; unaffected accepted shots may be reused if still compatible.

A one-minute request is a target final duration, not proof that a model makes one continuous sixty-second output. The planner proposes shot count and lengths based on reviewed recipe durations, complexity and dependencies. The user confirms the story, acceptable length tolerance, budget cap and execution strategy. A five-second recipe may mean about twelve shots plus titles, transitions or editing; story and contracts determine the actual count. Ten-minute work follows the same rule with greater budget, queue and revision cost.

A failed shot affects that shot and dependents, not the entire film. A submitted GPU job with unknown outcome is not silently sent again; reconcile the original attempt, object version and cost before any explicit recovery. A replacement node starts a new attempt and cannot submit a second result for the same attempt. Guangzhou verifies origin, pinned version, digest and complete decoding for each shot and the final MP4. Final assembly may be a reviewed compute task on a node; Shanghai receives only validation receipts.

## Visible conversation, queue and cost

A conversation plan card shows the story, approximate shot count, whether user material or platform image generation is needed, target length, available execution strategies and budget range. “Looks good” approves the plan only. Acquire required assets and a real quote, then obtain the user's maximum-spend approval before automatic background execution. Professional creation allows chapter-by-chapter changes before quoting; a post-quote change recomputes its affected scope and requires a fresh approval.

Show the project's witnessed stage and next action in the conversation: planning, awaiting approval, waiting for assets, quoted, waiting for a compatible device, generating a numbered shot, validating shots, assembling, validating the final film, playable delivery, paused, failed or cancelled. Show only server-reported queue position, completed shot count, progress and ETA for this project. When receipts lack a position or ETA, say it cannot yet be estimated. During disconnection, retain confirmed history and mark live percentages unverified. A long-film buyer can inspect accepted shots, see what blocks the next step, cancel work not yet started, and view completed charges and refundable balance. The final result plays and downloads in the conversation rather than being only a local path.

Formal acceptance must separately establish one-node short video, one-node long-film interruption and recovery, and distributed dependencies, concurrency and failure isolation. It must also cover admission of heterogeneous reviewed recipes, separately priced image work and asset rights, project budget caps, partial cancellation and settlement, real queue and progress receipts, and playable shots and final film. The fixed H3 graph, current single-shot guide and basic task status cannot establish that all three strategies are live.

The current client-reviewed input is one real first frame, one prompt and one MP4 for a single shot. The old fixed H3 publication recipe makes five seconds. The generic Comfy contract parser may accept a declared single-shot maximum of 120 seconds; this is a format ceiling, not evidence that a reviewed device can deliver a minute. Separately available platform image generation, project/chapter/shot orders, per-shot queue receipts, automatic assembly and an hour-long budget authorization are not wired yet. A new conversation may discuss a long-film plan but cannot turn it into a charged five-second task until the required contracts and supply pass real acceptance.
