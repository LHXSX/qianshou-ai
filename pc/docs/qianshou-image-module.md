# Qianshou image module: three supply sources and video first frames

English | [中文](qianshou-image-module.zh.md)

A user starts at one `@出图` entry, describes the image in natural language, then previews, revises and saves it in the conversation. Models, nodes and APIs are supply sources rather than separate buyer interfaces. A casual user may be asked about purpose, aspect ratio, style or an existing reference image only when needed. Advanced creation may expose composition, character consistency, reference images, seeds and variations, limited to parameters supported by the selected reviewed recipe. Image and video orders each require their own quote and authorization. With the user's approval, a delivered image can become a video first frame or an anchor asset in a video bible.

## Three sources

1. **A model on the user's own computer.** The user installs and verifies a reviewed image recipe on their PC and generates with their own resources. Local use does not authorize other people's orders on the machine. Tongyi's [Z-Image model family](https://github.com/Tongyi-MAI/Z-Image) is an initial candidate; Z-Image and Z-Image-Turbo are distinct recipes. Supported model versions, runtime, file digests, memory requirements, dimensions, inference parameters and license depend on the platform manifest and a real device test. If components are absent, show download size, source, license and disk requirements, then install only with the owner's approval. H3 video weights are not a universal image prerequisite.
2. **An ecosystem node taking orders.** After a real local image self-test, the owner may separately publish the image capability and authorize order intake. Shanghai assigns order metadata against the reviewed publication, recipe version, device capability, queue, price, privacy scope and success rate. The node generates the image and sends it to Guangzhou for independent verification, storage and delivery. A node may run Z-Image or another reviewed recipe; identical models are not required on every machine. The owner must be able to distinguish local use, publishable, under review, taking orders, paused, orders and earnings.
3. **A third-party cloud API.** A separately reviewed provider implements the same image task and result format. Its inputs, data destination, availability, dimensions, price, usage license, timeout and failure receipts must be explicit. User materials cannot be sent to an unauthorized API. Its price is shown separately from node offers, and the user confirms before an API call. If the provider becomes unavailable, quote a replacement source and ask for approval; do not silently change the model or price.

All three sources share the buyer meaning of `image.generate`. A publication separately declares text-to-image, image-to-image or editing support; an editing request cannot be passed to a text-only recipe just because the capability name matches. A publication binds capability version, model or service version, workflow digest, input restrictions, output format, dimensions and price. Local use and marketplace intake may reuse an executor, but they have different authorization and billing states. A cloud API uses a separate provider adapter rather than posing as a local device.

## Conversation, pricing and image assets

The conversation organizes the user's own words and asks one missing question at a time; optional details can be skipped. Show the intended image, aspect ratio, style, reference material, expected count and available sources before obtaining a real quote for one reviewed publication. Approving the creative plan is not approving payment. Changing the source, number of images or dimensions, or receiving a changed quote, requires a new quote and confirmation. Show witnessed order stages: waiting for local resources or a compatible node, running, upload verification, previewable result, failed or paused. Do not invent a queue position or ETA that the provider has not reported.

Each delivered image records the generating order, publication and recipe digests, source, content SHA, MIME, dimensions, permitted use, Guangzhou object bucket/key/version and verification result. When a user selects a real generated image as a video first frame, show its preview and obtain permission to use it. The video order then binds that exact object version and digest and checks the selected video recipe's format, aspect ratio and size requirements. Show image and video fees separately. Replacing or regenerating the first frame invalidates the previous video quote. Shanghai stores order and scheduling metadata only; it does not relay image bytes.

For long films, pin versioned character, scene and style references before allocating chapters and shots to compatible nodes. Replacing an image asset reschedules only shots that depend on it and shows the budget and progress effect. Each shot may read only the image versions it is authorized to use; a similar filename is not an asset identity.

## Current source and acceptance scope

The `image.generate` capability vocabulary exists, but marketplace intake, a cloud provider, Z-Image installation and verification, and generated-image-to-video-first-frame handoff are not connected. `commerce-image-workflow` v2 only previews a node route using model IDs supplied by the caller's image recipe. It neither verifies that the recipe was reviewed nor authorizes execution. The old v1 H3-plus-placeholder requirement has been removed; there are no persisted v1 orders or runtime consumers to migrate. The current video first-frame path accepts only a user's real local PNG/JPEG, and private local Comfy image trials are not marketplace orders. Before launch, each source needs a real generation, quote and authorization acceptance test, followed by cross-task asset acceptance for a generated first frame. Until then, do not present automatic first-frame generation as available or treat a solid-color fixture or a file path as a delivered image.
