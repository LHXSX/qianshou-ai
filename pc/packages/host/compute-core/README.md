# Qianshou compute core

English | [中文](README.zh.md)

## Summary

Read an authenticated compute catalogue, save bounded local plans, request Shanghai's final developer-task quote, and inspect workload progress plus owner-visible inline results. Run an already-admitted task through an exact local plugin version with verified input and output files. Cancellation drains execution before temporary files are removed. A locally registered executor still needs device and permission checks before starting; an online Shanghai declaration has no formal quote or wait time and cannot start an order. Catalogue entries do not establish online nodes, prices, spending quotes or settlement.

## Use this package

The conversation model receives the full history and can inspect separately the locally registered executors, Shanghai's shared capability catalogue, and current pool observations through read-only tools. It can discuss a task, a plugin idea or a distributed option without a sentence-level keyword classifier choosing a route first. A capability record is evidence for planning, not execution authorization. Exact package validation, owner consent, quote confirmation and Shanghai task admission remain Host-side gates.

Mount `@deepseek-ai/dsh-compute-core` in a Host composition that supplies the authenticated Connection service. Mount `@deepseek-ai/dsh-compute-core/tools` separately when an agent may inspect capabilities and save local plans. The bridge does not add these tools automatically or start another agent loop. The tool consumer accepts `observationOnly: true` for inspection-only presets: it retains capability and existing receipt reads, and omits `compute_dispatch_chain`, `compute_plan_draft` and `compute_submit`. The default retains these Host-owned planning tools; payment confirmation remains a separate owner action. The real Loader composition test exercises the mount, local routes, persistence, a native capability contribution and result consumption.

`POST /api/qianshou/compute/plans/confirm` stores an owner `approved` or `declined` decision on an existing local draft; it cannot spend. `POST /api/qianshou/compute/plans/quote` previews Shanghai's final task, amount, balance sufficiency, price basis and expiry. Its response omits the ticket and final spec; the Host retains the ticket in memory. The old `plans/publish` route and model tool reject first submission with `COMPUTE_QUOTE_CONFIRMATION_REQUIRED`. The Qianshou conversation card first displays the draft, then requests owner approval, then shows the live quote with its full inline input, exact amount and expiry. Only its separate amount-confirmation button calls the authenticated local `POST /api/qianshou/compute/plans/confirm-quoted` route with `{ id, quoteId, amount }`; no model tool exposes that action. The Host still checks the private quote ticket, current owner, amount, expiry, balance and durable submission ledger. An uncertain POST outcome disables another submit in the card and blocks every new key for that draft. `GET /api/qianshou/compute/workload?id=` and `GET /api/qianshou/compute/workload/result?id=` remain read-only. Old drafts without `authorization` or `workloadId` read as `pending` and `null`.

Configuration is owned by [the plugin entry](src/index.ts). Catalogue reads use the logged-in `accountSession` access token when that service is present; `tokenEnv` remains an explicit override for fixtures and profiles without an account plugin.

| Field | Default | Meaning |
|---|---|---|
| `baseUrl` | empty | Core HTTPS origin; empty disables remote reads. |
| `tokenEnv` | `QIANSHOU_CORE_TOKEN` | Optional access-token environment override. Logged-in `accountSession` tokens are used first. |
| `statePath` | `$DSH_HOME/qianshou/compute-plans.json` | Private plan path; task attempts use `.tasks`, and plugin builder recipes use `.plugin-drafts` siblings. |
| `timeoutMs` | `15000` | Complete upstream request timeout. |
| `maxResponseBytes` | `1048576` | Upstream JSON byte ceiling. |
| `maxRequestBytes` | `65536` | Local route JSON byte ceiling. |
| `maxDrafts` | `100` | Retained local draft limit. |
| `maxStoreBytes` | `4194304` | Byte limit for each local store. |
| `maxTaskRecords` | `1000` | Retained local attempt limit. |

The same input uploader serves file-capable market skills. The optional `POST /api/qianshou/compute/files/from-composer` route resolves existing attachment receipts only in the addressed live Session, verifies the complete bounded selection, and sends bytes directly from the PC to COS. It supports up to fifteen files and 16 MiB in total. Drafts retain verified storage metadata for quotation and restoration; uploading does not create an order or charge. An unsupported input contract or missing server price remains unavailable and never grants automatic dispatch.

A first-frame video request with both an image and natural-language prompt requires the live Shanghai task-type row to declare `capability_id=video.render`, an approved `qianshou.reviewed-video-task-input.v1` record and a matching `qianshou.reviewed-publication-selection.v1` publication. The video declaration binds `first_frame` to `input_manifest.files[0]` and `prompt` to `params.prompt`; the publication selection separately names its immutable artifact digest and reviewed task-contract SHA-256. The Host validates the single image type and size, uploaded object version, prompt and all four buyer-approved review identifiers before making a local plan. The image reference must use the dedicated reviewed-video input object key for the current core account; the Host checks that account again before quoting and paid submission. It sends the same `reviewed_publication` object in final-spec estimate and paid create requests. If the buyer selects a marketplace product, the Host also sends `selected_product` with the same publication ID. Shanghai must enforce both bindings before an end-to-end video quote. The Host re-reads the live catalog at quote and submission; any change rejects the old plan or quote before a chargeable task POST. A video artifact result also requires a same-account owner detail; a reviewed task returns a link only when its frozen contract and MP4 asset agree, while ordinary WebM/MOV tasks retain their links. A legacy form or an unreviewed graph cannot acquire this path from its display name or file extension. This source path remains a candidate until Shanghai signs and enforces the exact publication, the assigned Windows runner executes it, and Guangzhou independently accepts the MP4; PC-only tests do not prove public orders or video output.

`planCommerceImageWorkflow` v2 previews one `image.generate` node route using the non-empty model ID list supplied by the caller's reviewed image recipe. It does not verify that recipe, install a model, authorize execution or call an image provider. No H3 model is required by the image route itself. Local, marketplace-node and reviewed cloud-provider sources remain distinct product integrations.

### Private image trial

`imageTrial` is absent by default. An explicit `{ gatewayOrigin, tokenEnv, timeoutMs }` enables the research-only image route; the origin must be `http://127.0.0.1:<port>` for an operator-owned SSH forward to Guangzhou. `tokenEnv` names a Host environment variable. The token never enters responses or storage. The eight-step timeout defaults to 360000 ms and must exceed 300000 ms; 12/20-step jobs scale that budget by their sampling-step ratio. Upstream forwarding services must also allow those longer requests. The status endpoint describes configuration only, without claiming online supply or an official price.

An optional `researchImage: { gatewayOrigin }` routes new landscape/eight-step conversation requests through Shanghai's same-owner free research queue. The deployment must separately enable the Shanghai dispatcher and the contributing PC consumer; a ready API probe alone does not execute tasks. The Host records the original request, Session, owner and exact Guangzhou HTTPS origin before one metadata POST. A timeout or cold restart uses only the original request GET, including when that lookup returns 404. Shanghai returns task/attempt references; the Host fetches the corresponding PNG directly from Guangzhou with its private account credential and verifies length, SHA-256, PNG structure and 2048 × 1152 dimensions before displaying it. Retained UUIDs stay on their original backend, while separately configured square, portrait and 12/20-step trials keep their existing gateway. Accepted or uncertain research tasks cannot fall back to another generator. Queued/running/unknown work blocks updater restart; completed original-image delivery can resume with GET only. This fixed free path does not enable video dispatch, cross-owner workloads, prices or settlement.

The owner Connection exposes `GET /api/qianshou/compute/image-trial/status`, `POST /api/qianshou/compute/image-trial/jobs`, and Session-addressed `GET /api/qianshou/compute/image-trial/job` and `/image`. The POST accepts an immutable UUID, live `sessionId`, prompt and `square`, `landscape` or `portrait` preset. These map to 1024×1024, 2048×1152 and 1152×2048. Optional `steps` accepts exactly 8, 12 or 20; historical requests without it use eight. The status advertises `supportedSteps: [8, 12, 20]`; the dimensions stay fixed for all presets. A UUID cannot be reused with a changed step count. The Host returns a running receipt immediately, admits one operation at a time, and returns the same receipt for an identical UUID and payload. A changed payload is refused. Every receipt states `billing: research-no-charge`; this route creates no Shanghai order, quote or settlement.

New receipts persist `timing.submittedAt` as the Host acceptance time before submitting upstream. `timing.phase` is `generating` while waiting for the gateway image response, then `receiving` before downloading the returned PNG. This records observed request stages, not sampling progress or remaining time. Repeated reads and renderer reloads retain the same start time; older receipts may omit `timing`. The Host checks file integrity without an agent image review.

A refused connection on the initial gateway POST is recorded as `IMAGE_TRIAL_GATEWAY_UNAVAILABLE`: that connection did not deliver a model request. A disconnected response, timeout or interrupted Host still records an unknown outcome. Neither case automatically resubmits the job, and its UUID retains the original receipt. Receipt and image reads accept a matching persisted Session header when its Agent has left memory; they do not reopen the Agent or authorize a new submission. Missing or unreadable stored identity is refused, and the receipt must still belong to the addressed Session.

The Host requests the image from Guangzhou once, retrieves only its bounded relative `/img/5080/<file>.png` response, verifies PNG integrity and exact dimensions, and saves the image plus receipt under the private `statePath + '.image-trial'` directory. Results are capped at 16 MiB. Existing task-record and store-byte limits bound retained receipts; a full store refuses new trials. Owner reads rehash the saved image. An interrupted running receipt becomes `failed` with `IMAGE_TRIAL_OUTCOME_UNKNOWN` on reopening and is never resubmitted. Disposal stops local waiting without issuing a model-wide cancellation. The operator must supply the temporary gateway and node tunnels; this research path does not register commercial supply. The sole research image POST carries the original image job UUID in `Idempotency-Key`, including generated video first frames. The retained receipt still prevents another POST after an uncertain outcome or restart; the header alone does not establish that a legacy bridge forwards or enforces upstream idempotency.

### Private video trial

`videoTrial` is absent by default. An explicit `{ gatewayOrigin, timeoutMs }` enables the unbilled H3 research bridge at an operator-owned `http://127.0.0.1:<port>` SSH forward; the complete wait defaults to 1800000 ms. Both `qianshou/image-trial.patch.yml` and `qianshou/video-trial.patch.yml` retain the free same-owner `researchImage` route because Loader config patches replace the entire config. Deployment-specific compute settings must be copied into either overlay. The separately configured image route and its Host token are required for text-only video; one attached PNG/JPEG needs no image generation.

Previously rejected video downloads can be rechecked only by an explicit original-task query (`retryDelivery=1`). Host revalidates the captured job and recipe identity and the complete MP4 through GET; restoration alone does not retry a rejected result, and generation POST is never replayed.

The fixed 24fps trial requires 120 video samples. MP4 checks reconcile decode timing, composition offsets and the edit interval; malformed timing and incomplete files still fail. Container checks do not replace native playback acceptance.

The authenticated owner Connection exposes `/api/qianshou/compute/video-trial/status`, `POST .../jobs`, and Session-addressed `GET .../job` and `GET .../video`. The sole accepted profile is `qs_new4`, `landscape_C`, four steps, five seconds and 1344×768. Before submission the Host checks the current health/spec and binds first-frame, recipe and model SHA-256 values; completion must attest the same recipe/model and return an MP4 with the requested dimensions and duration. Media checks inspect container metadata and sample byte ranges, without an agent review or a guarantee of compressed-frame decoding. Inputs and checked MP4 bytes are capped at 16 MiB and remain in the private `.video-trial` directory.

The Host saves its original UUID, immutable input fingerprint and first-frame bytes before external generation; the browser retains only byte-free references. An identical UUID returns its existing receipt. Unknown POST outcomes are never resubmitted, including after a restart. A saved external job ID can resume by GET; a pre-submit interruption remains unknown. A completed parent can supply its saved original first frame for an explicit new UUID. Phase, elapsed time and optional upstream progress are observations. A recoverable upstream read failure retains the original ID and reports that reconciliation is pending. Every receipt states `research-no-charge`; the bridge creates no Shanghai quote, order or settlement, and does not register production supply.

### Private plugin builder drafts

The V1 native H3 declaration fixes the shipped runtime, actual execution recipe SHA, model-byte SHA and private configuration digest. The JSON-only source inventory is independent of runtime identity. `native-h3-device-proof` admits only purpose-enrolled Ed25519 signatures for the exact publication, owner, acknowledged device and Shanghai contract snapshot, then mints a process-local credential valid for at most 300 seconds. Serialized copies, stale receipts and tuple changes are refused. `native-h3-review` verifies a distinct short-lived pre-approval challenge; it cannot substitute for published installed-device proof. `native-h3-presence` verifies an independent twenty-field challenge valid for at most 120 seconds, bound to the existing reviewed sample, native configuration and current server-issued socket UUID. Presence is not another GPU sample or an approval. These helpers perform no GPU execution, upload, approval, pricing or settlement.

The authenticated `native_h3_adapter_update` frame carries a request UUID and at most sixteen exact fourteen-field native claims within 32 KiB. Its same-socket acknowledgment must match the request, current server connection UUID, accepted status and exact task set. Only that acknowledgment extends the connection's native task scope; a rejected, late or mismatched acknowledgment cannot activate it. Empty claims withdraw native scope without removing generic task scope. Updates share the existing eight-waiter bound and ten-second deadline, and disconnect rejects pending waiters. This is metadata admission, not an output or GPU receipt.

`GET /api/qianshou/compute/plugin-drafts` reads owner-local recipes. `POST` to the same route with `{ "spec": { ... } }` creates one; include the returned `id` to replace that draft. `GET /api/qianshou/compute/plugin-drafts/export?id=...` returns the full private design recipe for owner backup. `GET /api/qianshou/compute/plugin-drafts/preview?id=...` returns a downloadable deterministic structural package plan, its SHA-256, and per-operation checks against this device. The existing authenticated owner connection carries these routes. No request contacts a plugin market, package manager, model, workflow or Shanghai service.

Each recipe has a plugin identity and up to 16 freely named operations. Every operation declares a namespaced local model, workflow or tool ID such as `ollama:model-id`, `flow:workflow-id` or `tool:operation-id`, bounded input and output JSON Schema subsets, permissions, data scope, optional network origins, dependencies, and proposed OS, architecture, memory, disk, VRAM, input, output and duration requirements. Schema roots are objects; supported nested types are object, array, string, number, integer, boolean and null. Object schemas require `properties`, `required` and `additionalProperties: false`; external `$ref` and unknown keywords are refused. Binding references cannot be filesystem paths, URLs or commands. The private file uses atomic writes and owner-only permissions.

Saved and exported receipts say `private-draft`, `installable: false`, `dispatchable: false`, with adapter, real probe, signing and review all `pending`. A free operation ID is not registered in Shanghai's capability vocabulary. The export contains a design recipe, not a DSH bundle or signed installable manifest. A runtime adapter, real per-operation probe, confined execution process, package digest/signature and review are still required for general bundle installation or owner-approved public supply.

`HostPluginAdapterRegistry` holds exact operation bindings for local model, workflow and tool adapters. The creator context reads only current Host registrations; a listing does not prove execution. A private candidate requires each draft operation to match its adapter's binding, input/output schema digests, permissions, data scope, dependencies, platform, architecture and assets, with a fresh Host-submitted sample digest claim for the same draft revision. Disposing an adapter or changing the draft invalidates that claim. `plugin_draft_try_sample` requires one fresh owner approval, validates all inputs before any callback, runs only exact adapters registered by installed trusted Host packages, and validates each real output before recording a claim. Timeout or cancellation waits for the trusted callback to finish; a failed sequence revokes its claims. The data-only archive is verified and kept in a private local directory with a receipt that omits sample content and path. Sample input and output can contain private text, so review the archive before sharing it. The candidate and archive still report `executionVerified: false`, `installable: false` and `dispatchable: false`: an in-process trusted sample is not independent review, arbitrary third-party code isolation or bundle installation. The existing bundle installer cannot load this archive. No general adapter is registered by default; the installed private CSV seed is one concrete Host adapter and does not depend on ComfyUI.

A verified data-only archive can now be activated for PRIVATE local conversation use when its exact saved draft and every current trusted Host adapter match. `plugin_private_activate` asks the owner to approve the pinned package and candidate digests, then writes an atomic owner-only activation ledger. `listPrivatePluginActivations()` reads persisted installs and marks a row unavailable if its archive, draft revision or current adapter is missing. `plugin_private_run` asks for one-shot approval for the exact input digest and rechecks the archive, installed row, live adapter and JSON schemas before calling one trusted Host callback; callback duration is capped at two minutes. An owner-only invocation ledger reserves the input before callback execution, reuses a completed result for the same Host call ID and exact input, and blocks an operation after an uncertain failure instead of retrying it. A fresh owner-approved call ID can intentionally repeat the same input. Sample and private calls to the same registered adapter cannot overlap in one Host process. `plugin_private_uninstall` removes the exact activation row after owner approval, serialized with in-flight private calls; it leaves the archive and invocation history in private storage. The archive never supplies executable code, and this path does not create a public listing, Shanghai capability, order permission, sale or charge. A Host callback is trusted in-process code, not third-party isolation. An `active-private` row confirms current declared binding and schema matching, not a verified executable code digest or an independent review of a replacement Host implementation.

`buildOfflinePluginDeclaration({ draft, capabilityIds })` prepares a deterministic, data-only `qianshou.declaration.v1` ZIP that the Guangzhou intake verifier accepts. The caller supplies a capability ID for every operation; this library does not infer a Shanghai registration or upload the archive. It excludes samples, free-text descriptions, binding references, assets and private paths. The Guangzhou v1 format cannot carry network destinations, dependencies or workspace data scope, so the exporter refuses drafts using those features instead of omitting their claims. Its result is `built-offline-unsubmitted`, not an approved package, installable bundle, license or dispatch authority. Client export and upload are not yet connected.

`buildReviewableExecutionArtifact()` builds bounded canonical `qianshou.reviewable-execution.v1` JSON bytes from a private multi-operation draft, explicit capability IDs and a complete program for each operation. The versioned executor currently accepts only the bundled pure `qianshou.string-map.v1` interpreter: each program maps required flat string input fields to required flat string output fields with copy, trim or ASCII case conversion. `verifyReviewableExecutionArtifact()` reparses untrusted bytes and checks every implementation SHA-256; `evaluateReviewableExecution()` rechecks the bytes before running the packaged program without shell, filesystem, network or model access. Other tool bindings, workflows, local models, permissions, network origins, dependencies, workspace data and nonzero device requirements are refused. The artifact contains no draft description, sample, private path, model weight or credential; author-provided field names and plugin IDs still need review before submission. It is not the Guangzhou v1 ZIP, a DSH installable bundle, signed release, license, market listing or Shanghai order authority.

`plugin_reviewable_build` checks the exact saved draft revision, stores verified program bytes in an owner-private content-addressed directory and returns their SHA-256 without sending the bytes to the model. `GET /api/qianshou/compute/plugin-drafts/reviewable-execution/export?sha256=...` gives the authenticated owner an exportable JSON candidate after rechecking the disk bytes and hash. `plugin_reviewable_try_sample` requires fresh Host owner approval bound to the candidate SHA-256 and sample digest, then runs every operation through the bundled pure interpreter; sample inputs and outputs are never added to the export. A stale draft, unsupported binding, mutated file or missing sample fails closed. These steps create and test a private review candidate, but do not approve, install, publish, sell or dispatch it. A Guangzhou review and release contract must independently validate the same bytes before any market authority exists.

`ComputeService.preparePrivatePluginSubmission()` is a Host-only caller of that exporter. It requires the exact draft ID and revision, persisted private activation digests, and one explicitly supplied capability ID per operation. While holding the private archive and activation locks, it revalidates the saved sample archive, draft, activation row and current trusted adapters, then returns a redacted preview and ZIP bytes only to its Host caller. It never submits the declaration, grants a license or exposes either the private sample archive or the ZIP through a model tool, Connection route or Client Remote. An uninstalled, stale or tampered private plugin cannot prepare a declaration.

The package plan has a stable digest across draft IDs, timestamps and operation order. It includes only structural IDs, field names, input/output schema digests, permission and resource claims, and counts of dependencies and network origins; it does not gather source files, code, model weights, credential files, binding references, free-text descriptions or URLs. Platform, architecture, physical memory and free disk are checked from the current host; a missing disk observation is `not-probed`. GPU memory, local binding, dependency versions and actual execution remain unverified, so even a plan with no observed mismatch stays `pending` and cannot be installed, published, sold or used for orders. Owner-entered IDs and field names remain in the plan; review them before sharing. The full recipe backup also includes owner-entered free text.

An agent preset can separately mount `@deepseek-ai/dsh-compute-core/plugin-draft-tools` to receive only `plugin_draft_creation_context`, `plugin_draft_try_sample`, `plugin_reviewable_build`, `plugin_reviewable_try_sample`, `plugin_private_list`, `plugin_private_activate`, `plugin_private_run`, `plugin_private_uninstall`, `plugin_draft_mac_video_template`, `plugin_draft_model_candidates`, `plugin_draft_inspect_comfy_workflow`, `plugin_draft_probe_local_comfy`, `plugin_draft_preflight_comfy_workflow`, `plugin_draft_bind_comfy_workflow`, `plugin_draft_try_comfy_sample`, `plugin_draft_save`, `plugin_draft_install_mac_video`, `plugin_draft_read` and `plugin_draft_preview` plus a plugin-creation prompt. This narrow entry does not mount `compute_submit`. The read-only candidates tool uses only the last completed Host supply observation and selects `local-model` services that are not `unavailable`; it returns only their logical ID, name, verification state and observation time. It never calls `querySupplySnapshot`: that method would also reconcile Shanghai advertisements and write probe history. If no prior observation exists, the tool returns `{ "observedAt": null, "models": [] }`, which means unknown rather than no model installed. Cached candidates can be stale, and `pending` never means runnable. This tool does not scan arbitrary paths, download models, save a draft or test inference. When the owner asks to inspect local ComfyUI, its probe accepts only `127.0.0.1` on port 8188 by default or an owner-provided port, uses bounded GET responses without redirects, and returns the version, device VRAM, common model file counts and availability of up to 32 owner-named node classes. It never returns model filenames, raw system statistics, launch arguments, workflow contents or arbitrary HTTP responses. File counts and node presence do not prove inference works. For an owner-supplied ComfyUI API-format graph, the separate inspection tool accepts at most 256 KiB and 128 nodes and returns only node IDs, class names and candidate field names; it does not return prompt text, model filenames or other field values, read local files, contact ComfyUI or execute a graph. The owner must confirm the mappings. Only when the owner asks to compare that graph with this computer, the workflow preflight reads at most 32 distinct node classes through the same bounded loopback `object_info` reader. It returns the graph digest and each node class and direct model selector as true, false or unknown; it never returns prompt text, model filenames or raw node metadata. A matching selector is not an inference trial. The save tool requires an active agent session and owner request or agreement; the Host rejects unknown fields, paths, URLs, commands and invalid schemas. Read and preview accept only an opaque draft ID, while read without an ID returns brief summaries. The shipped CEO and dedicated creator presets mount this optional entry; a real conversation test is still required before treating the user flow as accepted.

The fixed `qianshou.mac-drawn-video@0.1.0` recipe retains its separate reviewed bundle installation path. `plugin_draft_mac_video_template` returns its exact approved design; after the owner asks to save it, `plugin_draft_save` stores an ordinary private draft. `plugin_draft_install_mac_video` accepts only that draft ID and revision, rejects every altered field and other adapter, checks this Mac has the fixed drawing tools, and obtains a fresh one-shot Host approval displaying the revision and package SHA-256. The Host materializes the pinned reviewed archive and sidecars from bundled bytes under the owner profile, calls the current profile plugin manager with that exact local archive, then verifies the installed archive, package files, active Loader row and registered executor. A restart-required result is reported as pending, never active. This unsigned local package is not a marketplace listing, public capability declaration, Shanghai order, sale or charge; the owner must still run a real local trial before judging its output. A later general creator needs reviewed adapter templates, isolated package builds, signed `qspkg` submission, Guangzhou review and account-bound Shanghai admission; this fixed template does not grant those steps.

The public creator lifecycle is still a development contract, not a working path: bind each approved draft operation to a reviewed runtime adapter; build a reproducible free artifact and per-operation trial evidence; sign the `qspkg` declaration and submit it for Guangzhou review; attach the approved listing to a publisher and an explicit license; then run archive inspection, signature/dependency/model/resource preflight, a fresh owner install decision, transactional installation and a local trial before any account-bound order admission. When the owner explicitly asks to make or save a plugin, that request covers a private draft save; the assistant checks the available facts, then saves it when required fields are known without asking again whether to make a plugin. Missing real bindings call for a read-only check or one necessary clarification, never invented IDs. For a reusable workflow noticed during another task, the agent should suggest a plugin only after a trusted task-completion receipt and reproducible evidence, then wait for owner confirmation before creating a private draft. The candidates tool exposes only models from the last completed local-supply observation; the ComfyUI service probe reads only bounded loopback metadata, graph inspection reads only a graph the owner provides, and graph preflight reads only bounded local node options for an owner-provided graph. Automatic workflow discovery, a general production adapter, repeatable inference acceptance, arbitrary packaging, signing and review remain separate work; the local single-image sample below is an isolated trial.

The binding tool accepts the owner-supplied API graph as JSON, never an arbitrary file path. It checks the graph size (256 KiB), node count (128), link targets, scalar input values, sensitive field names, paths and URLs, and the owner-confirmed prompt/output field mapping. Before writing, the Host approval service must return one audited `allowed-once` decision for this exact graph digest and draft version; missing or refused approval leaves the draft unchanged. The normalized graph and SHA-256 remain in the owner-only local draft file. Older v1 drafts without an asset remain readable. Model-facing reads, recipe exports and package previews show only a digest, node count and `stored-needs-trial` state, never prompts or model filenames. ### Explicit native H3 V2

[The V2 binding](src/native-h3-binding.ts) separates six public execution fields from the device's private owner configuration. Its fixed V2 ABI/runtime, actual recipe, model and first-frame SHA values determine the logical binding digest. [V2 evidence](src/native-h3-v2-evidence.ts) uses distinct schemas and signature purposes: review has nineteen fields, device proof twenty-two, presence twenty-two and configuration enrollment twenty-one. Configuration enrollment is bounded to 300 seconds, presence to 120 seconds and published proof to 300 seconds. V1 schemas, purposes and runtime pins remain unchanged; a V1 receipt or nonce cannot become V2 evidence.

A device registers its private digest through an authenticated same-connection configuration challenge and compare-and-set revision. Changing configuration, including changing back to old bytes, requires a later revision. V2 native adapter updates contain sixteen fields; V1 retains fourteen. Both share the sixteen-row and 32 KiB bounds. Only the exact current-socket acknowledgment activates the advertised scope.

[The ordinary V2 task lease](src/native-h3-task-lease.ts) is a separate eighteen-field top-level assignment credential. It binds the publication, source, logical identity, private digest, revision, device key, connection and actual worker/task attempt. The authenticated transport parses it before the HMAC bridge stores the original process credential; buyer parameters cannot mint or replace it. The assignment's account is the buyer, while the lease owner is the providing author. Queued and running tasks recheck the fixed tuple. A fresh proof for the same connection and revision can finish a task longer than 300 seconds; a changed tuple cannot replace an old attempt. These source tests establish admission behavior, not Windows rendering or paid delivery.

The [transport connector](src/node-transport.ts) parses authenticated offers and uses an explicitly bounded, sequential delivery queue. Invalid frames, queue overflow and consumer failure close the session; close drains any current delivery. Outgoing frames are rebuilt from allowed fields. A concrete transport still owns TLS, the actual worker protocol and endpoints. The [capability manifest](src/capability-manifest.ts) checks metadata and matching executor versions without loading downloaded code.

The [local plugin runtime](src/local-plugin-runtime.ts) is the execution admission seam after lifecycle activation. It rechecks the immutable manifest against the effect-owned executor registry before every task, quarantines missing or remote-only contributions, and never infers a capability from an installed file.

The [PC task surface](src/pc-task-surface.ts) projects one `qianshou.agent-router.v1` decision and an optional parsed local receipt into `qianshou.pc-task-surface.v1`. Local and cloud paths share that card. `executionAuthorized` and `dispatchable` stay false; an approved owner gate only selects `admit-local` or `hand-off-cloud` as the next action. A receipt is shown only for an owner-approved local path and omits result bytes, leases and charges.

The [resident task loop](src/resident-loop.ts) is a transport-neutral, pull-based tick seam for an idle agent. Each tick emits a redacted heartbeat, then serially hands verified offers to the coordinator with `interactionPolicy: 'autonomous'`; overlapping ticks are drained in order and `close()` rejects new work. A host adapter supplies the timer, resource observer, offer queue and network heartbeat. This seam does not open sockets, prompt a person, or execute plugin code.

The [node lease boundary](src/node-lease.ts) gives one task attempt an explicit owner node, expiry, revocation and idempotency key. Only the owner may accept or complete a lease, only the dispatch authority may revoke it, and acceptance after expiry is rejected. The state machine is pure and immutable; it is a contract for a future transport/persistence adapter and carries no media bytes, local paths, credentials, prices or upload URLs.

The [plugin-market planner](src/plugin-market.ts) verifies a parsed manifest, package digest, host range, explicit permissions and a deployment-supplied signature before returning a frozen staging plan. ## Lease-bound file transport

The internal `registrationOnly` option authenticates a device challenge session with an empty task allowlist and exactly empty execution capability arrays. It retains only hardware and tool facts already produced by the bounded local probe; a failed probe supplies no GPU, Python or H3 fact. It adds no Hello field. Before an accepted current-socket native update, the connection refuses running mode, task offers and lease operations; the resident seam also refuses active workload or capability heartbeats. A transport state of `ready` means authenticated challenge access. Native dispatch additionally requires the exact acknowledged native task scope and current owner authorization; generic execution continues to require its normal advertised session.

The candidate file consumer runs through the existing resident authorization, attempt and result lifecycle. Only a separately verified file provider may map an offer containing `file_contract`; ordinary offer shapes stay unchanged. Metadata parsing checks exact fields, SHA bindings, ownership and immutable versions, with depth 16, at most 256 values and an 8192-byte bound.

`EdgeWorkerConnection.readFileAttachment` uses its private current lease to request `/api/v8/files/attachment-read-credential`, checks every returned identity and digest, then reads the exact configured storage host/version and verifies size/SHA. `uploadFileArtifact` sends metadata to Shanghai and bytes directly to storage, retaining the confirmed version. Only that same uploaded manifest may be returned. `readPinnedVideoFirstFrame` is a separate Host-only candidate for a buyer-uploaded PNG/JPEG of at most 16 MiB. This reader has no production mixed-input offer, image-read credential endpoint or Comfy resident consumer; its unit tests do not establish Windows delivery.

`updateOwnerSupply` is the Host-only atomic switch command used by the owner master and service controls. It restores the authenticated owner/node inside the policy queue and merges only the requested mode or service grant into committed policy. The public identity-unknown `off` projection is never a write source. Matching bindings preserve other grants, rates and resource limits. An explicit first-use, legacy or different-owner/node command starts with empty grants and rates: mode alone authorizes no service; service alone leaves mode off. ## Known Limitations and Deferred Work
