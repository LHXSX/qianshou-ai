# @deepseek-ai/dsh-host-qianshou-vision

[English](README.md) | 中文

## 概述

`qianshouVision` Remote 回答这台宿主到底能不能看见屏幕，而且分三件事回答：有没有装上 computer-use 提供方、操作系统有没有给桌面授权、默认模型路线收不收图片。这里没有任何方法会挂载驱动、改动模型路线、安装提供方或授出任何权限。

## 三件事永不塌缩成一个「就绪」布尔

每件事都从拥有它的组件那里读，所以装了一半的状态仍然可诊断，而不是笼统地显示为一次失败。「驱动已注册 + 桌面已授权 + 模型只收文本」和「模型能收图 + 根本没有驱动」是两个不同的问题，它们又都不同于「驱动在但权限从未授出」。合成一个布尔会抹掉这个区别，把用户送到错误的设置项上。

`driver` 区分三种装配：`absent` 表示共享的 computer-use 服务压根没挂载，`service-only` 表示服务挂了但没有提供方注册，`registered` 则带上提供方的名字。提供方槽位按设计是独占且可选的：它的缺席是一条被上报的事实，绝不是激活失败，所以这个插件在完全没有视觉适配器的机器上照样能加载。

<a id="doc-section-2"></a>
## 权限探测归提供方所有

本包自己不做权限检查。它找名字以 `check_permissions` 结尾的工具 —— 裸名或带提供方前缀都算，这对应 Cua Driver 两种提供方的发布方式（原生是 `cua_driver_native__`，走 MCP 是 `mcp__cua-driver-mcp__`）—— 然后调它。当已注册的提供方没有发布这样的工具时，状态是 `unknown`、原因 `no-probe-tool`，且不会有任何工具被执行；绝不从配置去推断。

探测的回答只按数据读，绝不按文本读：`accessibility` 和 `screen_recording` 必须以布尔值出现在结果的 `structuredContent` 里，除此之外一律是 `unknown`、原因 `unrecognized-result`，而不是乐观地猜。`state()` 一律用 `prompt: false` 探测，只读当前授权状态而不弹出对话框。`requestPermissions()` 是用户的显式动作，用 `prompt: true` 探测，并且把 `probe_direct_capture` 钉死为 `false`，好让一次授权请求止步于辅助功能与屏幕录制，绝不额外附带驱动的直采同意。

<a id="doc-section-3"></a>
## 路线这件事问适配器，不问配置

能否收图这件事，走的是截图入库前同一条查询：设置里记录的默认模型路线，交给拥有该提供方的适配器去解析。适配器解析不出来的路线是 `unresolvable`，并且仍然把它尝试过的提供方与模型名带出来，用户才看得见是哪条路线失败了。适配器没有披露模态的路线是 `modalities-undisclosed`、`acceptsImage: null`，这与「适配器披露了一个空模态列表」不同：空列表本身是一种披露，所以读作 `acceptsImage: false` 且没有原因。

<a id="doc-section-4"></a>
## 配置

`probeTimeoutMs` 默认 15000，是一次读取里权限探测与路线查询共用的整毫秒预算，取值在 1000 到 120000 之间；冷启动驱动的慢机器需要的时间比热驱动多。销毁插件会中断已经在飞的那次读取，被这样掐断的探测和其他没有作答的探测一样上报 `probe-failed`。

<a id="doc-section-5"></a>
## 模型体验

### 屏幕状态读取

#### 模型看到什么

什么都看不到。本插件不注册任何模型工具，也不追加任何 Session 事件；两个方法只应答客户端 RPC。它调用的权限探测是提供方自己的工具，那个工具早已由提供方独立发布给模型，与本包无关。

#### 词元影响

无。本包不会让任何状态字段进入模型请求。

#### KV Cache 影响

同理为无：这里没有任何东西参与提示词组装。

## 已知限制与延期事项

<a id="doc-section-6"></a>

- 目前还没有客户端卡片，所以三件事能通过 RPC 取到，但没有窗口展示它们。等到有视觉提供方真正随用户安装的 profile 发布时再做卡片；在那之前，这些事实对主动来问的调用方是现成的。

- `requestPermissions()` 上报的是探测返回那一刻的状态，在 macOS 上就是用户还没回答系统对话框之前的状态。想要用户回答之后的状态，调用方在用户操作完成后再调一次 `state()`。
