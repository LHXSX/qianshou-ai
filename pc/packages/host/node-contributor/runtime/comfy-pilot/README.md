# Automatic Comfy API candidate

English | [中文](README.zh.md)

This Node library creates an owner-private, authenticated loopback API inside the existing PC Host. It uses only Node built-ins, reuses the running Comfy service and existing models, and requires no Python packages, generated scripts, public IP or manual workflow/path selection. It does not start, interrupt or restart Comfy, download a model, register Guangzhou, grant owner consent, qualify paid profiles or charge a fee.

The only supported recipe is the existing Qwen Image 2.1 INT8 ConvRot text-to-image graph at 2048×1152 and eight steps. These are fixed research recipe values, not official pricing tiers. The pinned template has an empty prompt and a private output prefix. Before creating an API, the factory reads Comfy device metadata, the actual three model lists and all eight node definitions; it checks input names, enum choices, numeric limits, link output types and the output node. Missing models or unknown workflows remain unavailable/unsupported, with no guessed graph or fallback download. The model file SHA is unknown; the returned workflow SHA identifies the fixed generated template, not a reviewed release receipt.

`createComfyPilot(options)` is an importable library factory, not an application CLI. Options supply a fixed `http://127.0.0.1:<port>` Comfy origin, private directory, API port, random private Bearer, deadline, result limit, durable opaque `ownerScopeId`, and asynchronous current-owner authorization callback. `ownerScopeId` identifies the persisted owner/device runtime and differs from the transient Sharing command `scopeId`. The callback separately checks `connect`, `execute` and original-job `recover`; new execution needs real idle-only/resource permission. Pausing can deny `execute` while preserving authorized original-job reads. A different owner scope cannot reopen the database. The Host must supply owner binding and close the factory on teardown; the library creates no consent on behalf of a user.

The private API exposes `GET /healthz`, `/v1/models`, `/v1/workflows`, `/v1/jobs/{requestId}` and `/v1/jobs/{requestId}/image`; `POST /v1/jobs` accepts exactly `{requestId, workflowId, prompt}`. Callers never send a node graph, model path, execution command, price, URL or tuning form. The factory preserves fixed recipe parameters and substitutes only the prompt and its own UUID-based output prefix. Authentication requires the exact private Bearer, and Origin/Cookie headers are refused. Upstream traffic uses direct loopback HTTP, no ambient proxy, no redirects, bounded positive Content-Length and a whole-request deadline.

SQLite synchronously records the unique UUID and execution right before the sole Comfy `/prompt` POST. Exact duplicate requests return the original record; changed requests conflict, and unknown work occupies the slot. The backend UUID is initially the caller's explicit prompt UUID and is immediately updated if the accepted response provides a different UUID. Lost POST responses never trigger another POST: recovery reads only the original saved history UUID. A backend that ignores caller UUIDs and loses the acceptance response cannot be automatically recovered; it remains unknown. This behavior does not claim recovery after Comfy history loss or a machine power failure.

A completed job reads only its fixed output node and matching UUID-based PNG filename. PNG signature, CRCs, IHDR dimensions, bounded inflation, scanline length/filter and exact Content-Length are checked before private delivery. Delivery errors preserve the original job, without regeneration. Private single-link partial files can continue only if their bytes match the original download prefix; final rename before the SQLite success commit also recovers. Windows ACL ownership and Windows native acceptance remain unverified. The factory does not perform Guangzhou formal media attestation or settlement.

Run CPU fixtures with `node --test packages/host/node-contributor/tests/fixtures/comfy-pilot-node-tests.mjs` from Mac-PC; eight cases use real loopback HTTP and SQLite, including owner changes during accepted POST and original-result GET. The focused Vitest runtime wrapper executes these cases. The real-Loader regression mounts the authenticated owner routes and the actual factory with metadata-only fixtures; it proves automatic creation after explicit consent, preserved existing Qwen service, and no GPU POST. These are source/CPU checks, not native Windows acceptance or a production generation receipt.

`SharingPilot` supplies typed internal `open`, `observe`, `submit`, `get`, `result` and `close` methods; the private origin and Bearer remain inside Host. The Sharing coordinator owns the factory under the saved owner/device, automatically matches the fixed Comfy recipe after current consent, reports actual metadata, and closes only its own loopback API on pause, revoke, account change or shutdown. A ready existing Qwen API remains running while this durable task wrapper reuses the same Comfy/models; no manual origin, graph or path switch is required. Guangzhou confirmation still requires the actual report/challenge ACK. The fixed zero-fee research relay is a separate next-stage consumer; its lease/upload end-to-end and native automatic creation are not proved by these CPU tests. Video has no supported local recipe and remains unavailable; formal paid installation, qualification and settlement stay independent.
